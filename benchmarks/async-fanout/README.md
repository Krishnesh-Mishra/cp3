# async-fanout - 10,000-timer join + 10,000 chained awaits

Two phases folded into one integer:

```
99898
```

Phase 1 (fan-out): create 10,000 zero-delay tasks in one synchronous step, all
before any of them completes, join them at once, and sum the resolved indices
(`0 + 1 + ... + 9,999 = 49,995,000`). `checksum = 49,995,000 % 1,000,003`.

Phase 2 (chain): 10,000 sequential awaits of an already-resolved value; every
step folds the loop index: `checksum = (checksum * 31 + i) % 1,000,003`.

## Expected output

```
99898
```

Re-derived independently by `../bench/oracle.py` (`async_fanout_checksum`):

```bash
python benchmarks/bench/oracle.py
# async_fanout_checksum()           = 99898
```

The oracle folds the two mathematical phases (the fan-in sum, then the chained
fold). It does not re-implement an event loop: the point is the fold order, not
a second scheduler.

## The entries are idiomatic, and phase 1 is not the same primitive everywhere

- JavaScript: `setTimeout(..., 0)` timers, fanned out with `Array.from` and
  joined with `Promise.all`.
- Python: `asyncio.sleep(0)` tasks gathered with `asyncio.gather`. `sleep(0)`
  is a bare event-loop yield, not a kernel timer, so Python does not pay
  timer-wheel costs in phase 1; that is the idiomatic zero-delay primitive in
  asyncio, and the asymmetry is stated here rather than hidden.
- Go: 10,000 goroutines send to a buffered channel while a `sync.WaitGroup`
  joins them; there are no timers. Phase 2 receives from a pre-filled buffered
  channel, so the receive never parks the goroutine.
- cp3: `sleep(0)`, which creates a real timer plus a `Promise<void>` per call,
  joined with `Promise.all`.

Phase 2 is the closer comparison across all four: every entry awaits a value
that is already available, 10,000 times in a row. Once process spawn is
subtracted, cp3's chained awaits cost about 0-4 ms (best to median), the same
order as JS (about 0-1 ms) and Go (about 0 ms on its best run, with a
noise-inflated median in this pass); Python's `asyncio.sleep(0)` path is the
outlier at about 243 ms. cp3's chained awaits are therefore not this row's
problem. The gap is phase 1: cp3's timer fan-out costs about 14 ms net of
spawn, against about 11 ms for Node's timers and about 2 ms for Go's goroutine
fan-in. The per-phase probe numbers in the wave report
(`build/scratch/rounds/WAVE-BENCH-JSON-ASYNC-REPORT.md`) carry the exact
commands and raw runs.

## cp3 landed-surface adaptations (exact)

1. `Promise.all` accepts only an array literal. An `Array<Promise<T>>` built in
   a loop is CP3002 (`src/codegen/src/emit/async.cpp`, `emitPromiseStatic`:
   "Promise.all over a non-array-literal input"). The 10,000-element literal in
   `cp3/main.cp3` is generated by `build/scratch/rounds/gen_async_cp3.py`.
2. The join result is not bound. Sema gives `Promise.all` no value type
   (`src/sema/src/checks/call_check.cpp`, `tryInferPromiseStaticCall` handles
   only `Promise.resolve` and `Promise.reject`), so the awaited value stays
   `unknown` and `values.length` / `values[i]` are CP3002. The fold therefore
   runs inside `tick` when each timer resolves: the same 10,000 additions, in
   resolution order, produce the same integer. Consequence for the landed
   surface: `tests/cases/async/promise_all_values.cp3` and
   `promise_all_length.cp3` currently fail with the same CP3002.

Both adaptations are ranked as fixes in the wave report.

## Why cpp/rust sit this row out

Neither the C++ standard library nor Rust `std` has a timer or event-loop
surface: there is no `setTimeout`-equivalent and no executor. A single
dependency-free file would have to hand-roll an event loop in C++, or add a
runtime crate (tokio, async-std) in Rust. The first measures a hand-written
loop, the second a dependency stack; neither is the language's standard async
surface. Node's timers, Python's asyncio and Go's runtime scheduler are all
standard-library surfaces, so the row compares those. The runner prints the
omission reason and still gates cp3 against go/js/python.

## Run one by hand

From each language's folder:

```bash
# go
go build -o async-fanout.exe main.go
./async-fanout.exe

# js
node main.mjs

# python
python main.py

# cp3 (regenerate the 10,000-element literal first, from the repo root)
python build/scratch/rounds/gen_async_cp3.py
cd benchmarks/async-fanout/cp3
../../../build/bin/cp3c.exe build main.cp3
./.cp3/out/main.exe
```

Rerun the row through the suite with `python benchmarks/run_benchmark.py
--only async-fanout --reps 3` and compare the `output` and `match` columns.
