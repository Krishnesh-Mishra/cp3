# CP3 v0.2.1 — networking and release tooling

- Version: `0.2.1` (`version.txt`)
- Release status (2026-11-10): the full Windows corpus on the packaged v0.2.1
  compiler: **3140 found, 3117 passed, 0 failed, 23 ambiguous** (all 23 are
  the tracked open spec questions, reported by the runner and never
  asserted; see `tests/cases/AMBIGUITIES.md`). Release artifacts are built and
  smoke-verified on both reference platforms (staged-tree `cp3 doctor`; the
  Linux tarball installed via `install.sh` and smoke-checked). arm64 package
  outputs remain marked `-untested`. Packaging (Windows MSI via WiX, Linux
  tarball) is documented in [`docs/BUILD.md`](../BUILD.md).
- Theme: the networking wave plus the release-tooling wave that shipped on the
  back of it

> **Supersedes the networking provenance in v0.2.0 notes.** v0.2.0's notes said
> "raw sockets integrated" — that was wrong about the source-visible surface
> (it described the native link rows, not importable APIs). This release ships
> the real surface.

## What shipped

### Raw TCP, UDP and TLS sockets are exported and live

`import`ing these names from `std/network` now resolves, type-checks and lowers
to the vendored native runtime:

```ts
import { createTcpServer, connectTcp, createUdpSocket, connectTls,
         createTlsServer } from "std/network";
```

- **TCP**: `createTcpServer(options?)`, `connectTcp(options | host, port?,
  timeout?)`, `TcpServer`, `TcpSocket` — loopback-verified echo roundtrip in
  the corpus.
- **UDP**: `createUdpSocket("udp4" | "udp6")`, `UdpSocket` with `bind(port[,
  address][, callback])`, `send(data, port, address)`, `"message"` events.
- **TLS**: `createTlsServer(options?, handler?)`, `connectTls(options | host,
  port?)`, `TlsSocket` — end-to-end handshake (SNI, ALPN, verify against the
  embedded Mozilla CA) verified on loopback.

The registry (`std_registry.cpp`), sema marker tables
(`networkMember` / `tryInferNetworkCall` / `inferNetworkConstruct`,
field tables, `tryInferNetworkCall`), codegen lowering
(`emitNetworkIdentifier` / `emitNetworkNew` / member-call tables), and the
LSP documentation tables are all wired. The vendored TCP/UDP/TLS runtime
sources were always built; the source-level surface only landed here.
The `tests/cases/stdlib/02/network/tcp/tcp_echo_roundtrip` and
`.../udp/udp_echo` fixtures (previously pinned `CP3304` / not-exported)
are rewritten as real loopback echo cases and pass in run mode.

### `cp3 upgrade` — self-update from GitHub releases

`cp3 upgrade` compares the running compiler (`cp3c version`) to the latest
public GitHub release of this repository and installs it:

- `cp3 upgrade` — check, then re-install from the release asset for your
  platform (Windows: the MSI via `msiexec /qb`; Linux: extract the tarball and
  run its `install.sh --force`, replacing the per-user install). The asset is
  verified against the release's `SHA256SUMS-<tag>.txt` first; a mismatch aborts.
- `--dry-run` prints the plan without doing anything; `--json` for machines;
  `--yes` skips the confirmation (required off a TTY).
- ARM64 packages are not published yet; `cp3 upgrade` says so rather than
  installing.
- At most one network check per 24 h feeds a one-line reminder at the end of
  ordinary commands (`cp3: X.Y.Z -> vA.B.C available; run \`cp3 upgrade\``).
  It is silent on any failure, never blocks, and `CP3_NO_UPDATE_CHECK=1`
  disables it entirely.
- The GitHub API is rate-limited without authentication (60 requests/hour).
  With the GitHub CLI installed, `gh auth login` is enough - cp3 reuses the
  CLI's stored credential. Otherwise set `CP3_GITHUB_TOKEN` (any scope is
  fine for public read access) or try later; `GH_TOKEN` and `GITHUB_TOKEN`
  are also honored.

### `cp3 update` — project dependencies to the latest GitHub release

`cp3 update [name] [--dry-run] [--json]` re-resolves each `source: "github"`
entry in `.cp3/lock.json` to the latest release of the same repository and
reinstalls it if the release is newer than the locked tag. `file:` and
`cp3 link` entries are left alone. `--dry-run` reports the plan;
`--json` prints a machine-readable report.

### `cp3c toolchain current` — the effective Clang in one line

`cp3c toolchain current` prints the toolchain cp3c will actually use (plus
where it comes from) on one line. `cp3 doctor` now uses it instead of `PATH`,
so a configured toolchain is reported correctly (the previous PATH-only
discovery showed `(none found)` for a fully working setup).

### `cp3 init` is one implementation, not two

`cp3 init` previously existed twice: the shim (Windows batch / POSIX shell)
wrote a bare `package.json` with no prompts, and `cp3c init` asked typed
answers. The shim now forwards `init` to `cp3c` like every other command, and
`cp3c init` asks interactively: arrow-key menus for project type and
type-system, then questions for name, description and author. Scripts are
scaffolded as `start` / `verify` / `build`. `--force` overwrites the scaffold;
the `src/index.cp3` entry matches the spec (the `src/main.cp3` divergence is
gone).

## Packaging

- `vendor/tools/build-matrix.py` is the matrix build/stage/package driver
  used to produce the release artifacts (`--targets windows-x64,linux-x64`);
  it smoke-checks each produced binary.
- Artifacts: `cp3-0.2.1-windows-x64.msi`, `cp3-0.2.1-linux-x64.tar.gz`,
  `SHA256SUMS-v0.2.1.txt`. arm64 outputs remain unbuilt and `-untested`.

## Release notes deltas vs v0.2.0

- Raw sockets: v0.2.0's claim of "raw sockets integrated" was inaccurate for
  the source-visible API; corrected in v0.2.0's notes and shipped for real here.
- `cp3c toolchain current`, the self-update and project-update commands,
  unified `cp3 init`: new user-visible commands in this release.
- `docs/site/` is regenerated; the embedded `cp3 docs` document set ships the
  above command surface.
