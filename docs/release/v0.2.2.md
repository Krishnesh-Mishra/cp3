# CP3 v0.2.2 — compiler fixes and resolution of the open spec questions

Release date: 2026-11-10. Windows x64 corpus-verified; Linux x64 builds through
the packaging flow (full corpus not re-run on Linux for this release).

**Headline:** the installed compiler can build ordinary programs again —
the v0.2.1 MSI/tarball was missing `cp3/typed_array.hpp`, so every array-using
program failed at the C++ step. v0.2.2 ships the header, a smoke test that
exercises arrays in the staged package, and a large set of annotation-resolution
and diagnostic fixes driven by the redis-cp3 implementation feedback, with every
issue adjudicated.

## What's new

### Imported and exported type names resolve in annotation positions

- `export interface`, `export type` (including self-recursive aliases) and
  `export class` register their names for same-file annotations (they were
  previously unresolvable everywhere, CP3302).
- A class field, constructor parameter or method signature can name a type
  imported from a local module or from `std/*` —
  `sock: TcpSocket | undefined`, `m: Map<string, number> | undefined`.
- `Array<T>` is accepted in type positions (equivalent to `T[]`).
- Missing generic type arguments at `new` default to `undefined`
  (`new Box()` ≡ `new Box<undefined>()` when no argument or class default
  exists); excess arguments remain CP3418.

### Flow analysis

- `if (x === undefined) break;` (and `continue`) narrows `x` for the rest of
  the loop body, matching the straight-line `return` form that already worked.

### Async return semantics

- An `async` function adopts a returned promise: `return parts.promise` in
  `async f(): Promise<C>` type-checks and lowers to `co_return co_await ...`,
  matching JS thenable adoption.

### Diagnostics

- **CP3411** (mixed-type arithmetic and width conflicts) now suggests the fix
  with the offending operand's source text — `convert 'x' with parseTo(x,
  i64)` — and prints the suggestion in non-pretty (CI) output.
- **CP3510** (warning): a `return` inside `finally` — cp3 ignores its value
  (JS would let it override).
- **CP3511** (warning): a `type: "package"` entry module that exports nothing
  — flagged at check time, not only at pack time.
- **CP3520** (warning): loose `==` against a `null`/`undefined` literal.
- **CP3709**: a class field declared without an initializer and never assigned
  in a constructor is a compile error (mark it `!:`).

### Casts and literals

- `[] as string[]` compiles; the unrelated-cast diagnostic prints real type
  names.
- `return [];` from a `string[]`-returning function type-checks.

### Interop

- `package.json` and every CLI JSON document accept a UTF-8 BOM.

### Packaging

- The MSI and the Linux tarball now ship the `cp3/typed_array.hpp` include
  tree. Without it, v0.2.1's packaged compiler could not build any program
  that used arrays — every generated prologue includes that header. The
  packaged smoke test now builds and runs an array-using program so this is
  caught before release.

## Verification

- Windows x64: full corpus on the packaged v0.2.2 compiler (see
  `benchmarks/results.md`).
- Linux x64: tarball builds via the packaging flow; the full corpus was not
  re-run on Linux for this release.
- Tests are written before the implementation; every fix carries a regression
  case (`tests/cases/v0-2-2/`), and the 23 previously-ambiguous cases were
  resolved and pinned as ordinary expectations.

## Spec resolutions (all 23 former ambiguities)

See `tests/cases/AMBIGUITIES.md`. Notable: loose `null == undefined` is
`false` (flavor-exact, with CP3520), `finally { return }` does not override,
`enum` members print the underlying integer, spreading `number[]` into fixed
arity is accepted, `JSON.parse` requires `<T>`, `type X = ...` is a keyword,
both bare and `./` specifiers resolve (package wins ties), `for...in` yields
`number` indices, `reduce` without an initial value works (first element),
function declarations hoist, `let`-capture loops are fresh per iteration,
`export default function` is legal, and a worker crash never takes the main
thread down (it surfaces as an `error` event on the worker handle).

## Known limitations

- A class field typed `object | ...` has no C++ representation (CP3401 at
  build); `check` does not prove the native step. Use a function-typed field
  capturing the handle (closures over native handles lower correctly).
- The Linux corpus was not re-run for v0.2.2.
