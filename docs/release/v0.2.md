# CP3 v0.2.0 — TypeScript compatibility

- Version: `0.2.0` (`version.txt`)
- Theme: ordinary TypeScript class and error-code should work in CP3, on the
  way to native executables with no hidden runtime machinery
- Release status (2026-11-09): Windows is the reference platform for corpus
  verification in this wave; the Linux corpus rerun is pending the final
  Linux rebuild. arm64 package outputs are marked `-untested`. Release
  packaging (Windows MSI via WiX, Linux tarball) is documented in
  [`docs/BUILD.md`](../BUILD.md); the tag is cut from `version.txt`.
- Scope ledger: [`ROADMAP.md`](../../ROADMAP.md) (§v0.2.0, marked Done);
  design notes under `docs/design/`

CP3 v0.2 is a compiler and standard-library wave. There is no runtime feature
flag to turn on: rebuilding your application with the v0.2 compiler is enough
for the source-level changes to take effect.

## What shipped

### `std/json` — the file-oriented API and inline `<T>` parsing

`JSON` (imported as `import JSON from "std/json"`) gains five members,
alongside `JSON.parse<T>` / `JSON.stringify`:

| Call | Result | Behavior |
| --- | --- | --- |
| `JSON.parseFileSync<T>(path)` | `T` | Reads and parses like `JSON.parse<T>` on the file's text |
| `JSON.parseFile<T>(path)` | `Promise<T>` | Same, on the async fs path |
| `JSON.stringifyToFileSync(path, value)` | `void` | Serializes and **overwrites** `path` (raw write, no append) |
| `JSON.stringifyToFile(path, value)` | `Promise<void>` | Same, async |
| `JSON.verify<T>(text)` | `boolean` | Same checks as `JSON.parse<T>`, never throws |

- `<T>` is **required** on `parse`, `parseFileSync`, `parseFile` and
  `verify`; a bare call is a compile error (`CP3208`). The stringify family
  (`stringifyToFile(Sync)`) takes **no** type argument — the value's own
  type is all the serializer needs.
- `T` may be a primitive, a primitive array, a registered plain-record
  interface, or an inline object annotation (`JSON.parse<{ x: number }>(text)`);
  inline object shapes lower through the same record engine, including nested
  plain records and `?:` members (absent-with-no-error).
- Every failure of the parse/verify surface throws (parse side) or rejects
  (async side) with the same `json::ParseError` class `JSON.parse<T>` uses;
  an `fs` read error is boxed into it. `verify<T>` never throws: it returns
  `false` for malformed JSON, a duplicate key anywhere in the text, a
  missing/mistyped required field, or a shape mismatch. Extra keys are
  ignored; keys match case-sensitively.
- `stringify(value, replacer?, space?)` shipped earlier in the 0.2 line: an
  ECMAScript replacer callback `(key, value) => replacement` (returning
  `undefined` omits a property), a `string[]` allowlist, `space` as
  `number | string`, with a legacy numeric second argument still accepted as
  indent.

Fixture family: `tests/cases/stdlib/02/json/file/`. See
[`docs/content/03-standard-library/09-json.md`](../content/03-standard-library/09-json.md).

### Fresh-literal `Object.assign` merge semantics

`Object.assign(target, source1, source2, ...)` with a **fresh literal** target
(`{ a: 1 }` written inline) now produces a *new* object whose shape is the
union of every source, in JS key order, later sources winning a duplicate key,
with three or more sources supported. A **reused binding** as target keeps its
fixed declared shape: a source carrying a key the target does not declare is a
compile error that points at the spread form (`{...t, ...u}`), which cp3 does
support. `null`/`undefined` sources are ignored; a nullable object source is
allowed and null-checked at runtime.

### Virtual dispatch for overriding methods

A method that has an override **anywhere in the program** now lowers to a C++
`virtual` member; a method with no override anywhere stays a direct
(static-bound) call. Analysis is program-wide (all units of a program, before
any unit is emitted) and fails closed:

- an unmodelable base (`extends expr`, a non-named base type, an unresolvable
  base name, or a base cycle) marks **every** non-static, non-private method
  of the class `virtual`;
- duplicate class names widen the analysis to every candidate base (overmark,
  safe direction);
- abstract members in the set are emitted as pure virtual (`= 0`), so vtables
  never reference an undefined symbol;
- static members, `private` members and `#private` members, constructors,
  accessors, and fields are never `virtual`.

`super.method()` remains a base-qualified direct call. Dispatch flows through
`Ref<Base>` and interface thunks as usual. Fixture family:
`tests/cases/classes/01/virtual_dispatch/`,
`tests/cases/classes/01/opt_guard/e_devirtualize_006`…`009`, `e_abstract_044`.

### Enum arithmetic numericness (TS parity)

Number-backed enums read as numbers in arithmetic
(`+ - * / % ** & | ^ << >> >>>`) and in relational operators; any pair of
number-backed enums (same or distinct types) participates, and a number-backed
enum is assignable to `number`. The result type of arithmetic is `number`.
String-backed enums keep their rejections (`CP3411` / `CP3406`); `number` →
enum stays `CP3401`. This supersedes the earlier "distinct enums stay an
error" reading that the enum lanes reported against `j_enum_015`.

### Parallel call diagnostics

`parallel.for`, `parallel.reduce` and `parallel.run` calls are now checked in
the front end instead of failing late (or never):

- an unknown member (`parallel.wait`, `parallel.spawn`, …) is a
  member-not-found diagnostic;
- arity mismatches (`parallel.for` takes a range and a closure; `reduce` takes
  a range, an initializer and a closure);
- the first argument of `for`/`reduce` must be a range;
- the closure parameter count is checked (`for`: 1; `reduce`: 2), and
  `parallel.run` arguments must all be closures.

### Annotations and constructors

- `readonly T[]` and `readonly [A, B]` qualifiers are accepted on
  array/tuple type annotations. Read-through only; no runtime cost.
- `Array<number>(n)` — the explicit type argument on the array family
  constructor is accepted (previously rejected; pinned by `j_ta_003`).
- Optional class fields (`x?: T`) spell as `std::optional<T>` struct members
  and read as `T | undefined`.

### Async and promises

- A class method declared `async` lowers to a coroutine body.
- `new Promise<T>(executor)` is implemented: the executor runs synchronously,
  `resolve` is typed `(value: T) => void` (nullary for `Promise<void>`), and
  `reject` is typed `(reason: Error) => void` — rejection reasons are
  `Error`-typed, matching the only-`Error` throw law and the runtime resolver
  ABI.
- Promise combinators (`all`, `race`, `allSettled`, `any`) treat plain values
  as already-resolved promises (JS parity), including mixed literals
  (`[1, Promise.resolve(2), 3]`), wrapped per element. A mixed non-literal
  source is rejected with a clear diagnostic.
- `.then`, `.catch` and `.finally` handlers are typed functions:
  `.then` handler receives the promise's value type (nullary for
  `Promise<void>`), `.catch` receives the rejection as `any` (observes
  anything; cp3's `catch` binds `Error` at throw sites), `.finally`'s handler
  is nullary.

### Toolchain / sysroot

The sysroot probe now requires resolving `__local_stdio_printf_options`
(`corecrt_stdio_config.h`) at link time. Sysroots whose UCRT predates that
export fail the probe, and the tool falls back to an explicit `--sysroot`
instead of declaring a broken sysroot ready — previously this surfaced as
link failures in standard-library translation units on stock LLVM against
older MinGW environments. Clang's MinGW `--gcc-toolchain` flag is no longer
used; `--sysroot` is the active re-pointing mechanism.

### Un-annotated literal bindings take the `typeSystem` native default

Under `typeSystem: "cpp"` or `"rust"`, an un-annotated binding whose
initializer is a plain integer literal (`const port = 8080;`, `const a = -5;`)
now infers a native integer instead of `number`: `i32` when it fits (C++ `int`
and Rust `i32` share the canonical id), escalating to `i64` and then `u64`;
literals beyond `u64` keep `number`. Fractional and exponent spellings
(`2.5`, `2.0`, `1e3`) keep `number` (f64/`double` is the float default, which
is `number` here). Negative literals are included (`-5` is an `i32`). TypeScript
projects are unchanged. `parseInt`/`parseFloat` remain legacy
JS-compatibility globals and always return `number`; use `parseTo<T>` for
exact native widths. As before, a join that contains `number` absorbs the
literal (`const port = cond ? parseInt(s) : 8080; // number`) — the default
applies when the initializer is a bare literal. Fixture family:
`tests/cases/types/02/native_project_cpp/literal_default/` and
`tests/cases/types/03/native_project_rust/literal_default/`. See
[`02-types.md`](../content/01-language/01-variables-and-bindings/02-types.md).

### Also landed in this wave

- `String.prototype.replace`/`replaceAll` accept a `RegExp` argument
  (literal replacement).
- Empty array literals with pattern defaults destructure (`const [x = 7] = []`);
  the rest arm of an array pattern clamps instead of reading out of bounds.

## What changed behaviorally

- **`Object.assign` with a fresh literal target**: the result is the merged
  shape (JS key order, later sources win), not the target's declared shape.
  Code that printed or enumerated the result can observe the new key set and
  order. Reused-binding targets are unchanged in shape; only the rejection of
  source keys not on the target is enforced (see the merge rules under
  "Fresh-literal `Object.assign` merge semantics" above).
- **Enums**: number-backed enum arithmetic, relationals and enum → `number`
  assignment that previously failed to compile now compile. Code that relied
  on the diagnostics (`CP3411`/`CP3406`/`CP3401`) at those sites will compile.
- **`parallel.*`**: malformed calls are now front-end diagnostics, reported
  by `cp3 check` as well as at build time.
- **`j_ta_003`**: `Array<number>(3)` is accepted and prints `3`.
- **`e_parse_to_050`**: fixed; `parseTo<u64>(n)` from a `number` binding
  checks.
- **Optional class fields**: reads of an absent `x?: T` now yield `undefined`
  with a statically visible `T | undefined` type; the struct member lowers to
  `std::optional<T>`.
- Verified green in the current tree (against the post-landing compiler):
  `e_nullable_028`, the JSON file API fixtures
  (`tests/cases/stdlib/02/json/file/`), `d_json_004` and `d_json_005`
  (inline-object type arguments).

## What was fixed

- **Sysroot probe** (see above). This resolves the family of "linking failed
  (exit 1)" corpus cases seen on stock LLVM/MinGW against older UCRT: 46
  previously link-failing cases were re-checked and now pass.
- **Duplicate translation units**: runtime TUs named by multiple native rows
  were linked twice; strict linkers (GNU ld) rejected the program. Rows are
  now inserted exactly once.
- **JSON inline-record reification**: inline and interface record shapes
  register their model so `JSON.parse<T>` / `verify<T>` / `parseFile<T>` link
  even when no other `parse<T>` use names the shape.
- **`web_helpers`** passes over loopback.
- **`network_threads_ws_upgrade`** passes isolated.

## What is still open

- **Full corpus rerun on the final binary is pending.** The 2026-11-09 corpus
  logs predate the enum widening, the fresh-literal `Object.assign` merge,
  the parallel-call diagnostics and the sysroot probe rebuild; their failures
  reflect the pre-landing compiler. The Linux corpus rerun is likewise
  pending the final Linux rebuild (the tree configures and builds under
  WSL with Ninja; see [`docs/BUILD.md`](../BUILD.md)). Windows is the
  reference platform for this release.
- **`h_assign_001`** (`Object.assign({ a: 1 }, { b: 2 })` expected to print
  `a,b`): the fresh-literal merge landed in this release; the fixture has
  not yet been confirmed green on the final binary.
- Enum fixtures pinned against the pre-widening rules (e.g.
  `tests/cases/enums/opt_guard/j_enum_015`) predate the numericness change
  and the widening; the full rerun will settle them.
- **arm64 packages** carry the `-untested` marker (file name, manifest and an
  `UNTESTED.txt` in the staged tree; the Windows arm64 stage also drops the
  MinGW UCRT-incompatible vendored libs and records an unverified compiler
  version). Vendored arm64 archives (openssl, xxhash, simdutf, pcre2,
  libsodium, libuv, uWebSockets) landed with SHA-256 provenance, but nothing
  has been run on arm64 hardware.

## Known limitations and deviations

- `Record<string, V>` canonicalizes to `Map<string, V>`. The runtime
  collection view (Map/Set/`ReadonlyMap`/`Record` forms) is **mutable** at
  runtime; cp3 enforces its fixed shapes at compile time and does not layer a
  runtime immutability contract on the view types.
- **No tracing GC.** Lifetime is reference counting. Strong-reference cycles
  keep objects alive; use a `weak` field to break an ownership cycle. The
  compiler-injected automatic cycle handling (ROADMAP stages 2–3) is not
  enabled; weak links are manual, and their semantics are documented in
  [`docs/content/02-runtime/09-reference-cycles-and-weak-links.md`](../content/02-runtime/09-reference-cycles-and-weak-links.md).
- **No catch-all type.** `JSON.parse` without a type argument is a compile
  error (`CP3208`), not `unknown`-with-runtime-everything; see
  [`docs/content/03-standard-library/09-json.md`](../content/03-standard-library/09-json.md)
  and [`docs/content/01-language/01-variables-and-bindings/02-types.md`](../content/01-language/01-variables-and-bindings/02-types.md).
- **`verify<T>` cannot distinguish "unparseable" from "shape mismatch".** Call
  `JSON.parse<T>` in `try`/`catch` when you need the distinction.
- **Rejection reasons are `Error`-typed.** `Promise.reject(v)` and an
  executor's `reject` both carry `Ref<Error>`; a non-`Error` reject value is
  not the supported path (the throw-only-`Error` law applies).
- **Class methods declared `async`** lower to coroutine bodies on the one
  event loop; `async` is not threads.
