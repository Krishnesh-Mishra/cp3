# 23. Open design questions

The concept is considered technically sound; what remains is specification and real engineering, not a blocking unknown.

**Resolved since the initial draft** (kept here for history, language decisions only - see [CLI-README.md](../cli-tooling/00-overview.md) for tooling/package-manager history): **`let`/`var`/`const` mutability corrected** - an earlier draft had `let` and `const` both immutable with only `var` mutable, which was backwards relative to real JS; fixed so `let` and `var` are both reassignable and `const` is the sole immutable binding, matching real JS exactly ([§8](08-variable-bindings.md)) · reference-cycle handling (originally auto for different-field cycles + `weak` for same-field cycles - **superseded: every cycle is broken with an explicit `weak`**, [§11](11-reference-cycles-the-weak-keyword.md)) · closures capturing plain variables (a captured, reassignable `let`/`var` lives in a shared refcounted cell, shared across closures, same cycle rules, [§10](10-memory-management.md)) · threading model (worker files, copy-in only, no shared memory, no user-facing atomics or locks) · async model (JS-style event loop; a paused function's state lives in its heap-allocated coroutine frame) · base type system (TS default, overridable via `typeSystem`, `r_'...'`/`c_'...'`/`ts_'...'` prefix escape hatches, C++-style implicit numeric widening by default with an opt-in strict flag, literal syntax always cp3's own) · optional/nullable types (`undefined` and `null` both supported, unions backed by `std::variant`) · mixed-type arithmetic rules (compare/store freely, operate requires explicit conversion) · error handling (JS-style `try`/`catch`, no separate exception hierarchy) · `ref` by-reference parameters ([§12](12-pointers-references.md)) · generics (angle-bracket syntax, classes and functions) · class model (single inheritance, multiple interfaces, `abstract`, access modifiers, `static`, always-bound `this`) · enums (plain and string-backed) · operators (`==`/`===` both kept, JS-style truthy/falsy in `if`, `?.`/`??` kept) · control flow (`switch` with JS fall-through, all 3 `for` variants, full destructuring, spread/rest, dense arrays only - no sparse holes) · comments and literal syntax (JS-style) · generators and decorators explicitly **skipped for v1** · prelude files (`_prelude.cp3`/`.same.cp3`/`.weak.cp3` - strong/folder-only/stoppable-recursive injection, [§18](18-modules-imports.md); empty files still wall off weak injection; multiple prelude files per folder allowed and stack) · standard library architecture (authored in cp3 itself via native import, not hand-written C++; bundled with the compiler, never a separate install - [§20](20-standard-library.md)) · std lib expanded (`path`, `os`, `events` [pure cp3], `crypto` [libsodium-backed: `randomUUID`, `sha256`/`sha512`, `AES256`/`AES256Decrypt`], `env` [built on `process`]; `setTimeout`/`setInterval`/`clearTimeout` placed as core language builtins, not std, since they're tied to the event loop) · `std/server` (Drogon) and `std/webview` both considered, then **deliberately removed** from the core plan entirely - not deferred, just dropped; either could become an ordinary third-party package later, with no official status assumed · `JSON.parse<T>` runtime-validates against `T`'s shape and throws (catchable via existing try/catch) on mismatch - this requires generics to carry **reified runtime type metadata** for classes/interfaces used this way, a real new engineering requirement beyond what plain compile-time-only generics needed before · `Date` made immutable (every "change" method returns a new `Date`, avoiding JS's classic mutable-`Date` footguns) · `process.exec` (buffered, single result) vs `process.spawn` (event-based streaming) split, matching Node's distinction exactly · toolchain detection & auto-install (`cp3 init`/`build`/`run` check for an available C++ toolchain first, offer to install Clang/LLVM directly if none found, [CLI-README.md §1](../cli-tooling/01-compilation-pipeline.md)) · package `export default` statement made mandatory for `"type": "package"` (build fails without it), distinct from the still-optional reserved `default` key within it ([§19](19-c-cpp-interoperability.md)) · `Map`/`Set` included, 1:1 wrapping `std::unordered_map`/`std::unordered_set` · `buffer` included as its own std module · interfaces made **structural** (TS-style, no explicit `implements` required - a real subsystem comparable in scope to TypeScript's own type checker, implemented via compile-time shape-checking plus an automatically-generated type-erased wrapper for polymorphic storage, [§15](15-classes.md)) · custom classes can plug into `for...of` via `begin()`/`end()` methods, mapping directly to C++'s existing range-based `for` mechanism ([§6](06-control-flow.md)) · `number` confirmed to always mean a 64-bit double under the TS-default type system, with no automatic inference to a narrower integer type - real integer performance requires explicitly reaching for the `r_'...'`/`c_'...'` escape hatches ([§3](03-type-system.md)) · **concurrency model expanded to two distinct mechanisms**: `parallel.*` (`parallel.for`/`parallel.reduce`/`parallel.run`, shared-memory structured data parallelism backed by TBB, capture rules: closures always take a non-owning borrow rather than a refcounted handle - originally because a shared non-atomic refcount was a race, now because atomic refcount contention would serialize the parallel loop and the synchronous call already guarantees lifetime - and disjoint index-writes through a loop's own provided index are the one named safe-write exception, [§13](13-concurrency-parallel-and-workers.md)) alongside the existing `worker` (isolated, message-passing, [§13](13-concurrency-parallel-and-workers.md)) · **memory management strategy simplified (see the "Memory-model simplification" entry below - supersedes the earlier escape-analysis-first design)**: value types on the stack, reference types always heap-allocated behind atomic-refcounted `std::shared_ptr`, cleanup by C++ RAII, explicit `weak` for cycles ([§10](10-memory-management.md), [§11](11-reference-cycles-the-weak-keyword.md))

**Resolved for beta one** (closing out items that were previously open - language decisions; see [CLI-README.md](../cli-tooling/00-overview.md) for tooling/package-manager items):

- **`while` and `do...while` added to [§6](06-control-flow.md) - a genuine, previously-missing control-flow gap, not a minor omission.** Earlier drafts defined `switch` and all three `for` variants but never mentioned `while` at all, despite it being fundamental JS and despite the doc's own vocabulary list implicitly assuming it existed. Maps directly to C++'s native `while`/`do...while` - zero new engineering, same as the `for` variants.
- **`finally` added to [§7](07-error-handling.md) - the same class of gap as `while`.** `try`/`catch` alone isn't "the same model as JavaScript" without it; `finally` is used constantly for cleanup. Compiles via a generated C++ scope guard (a small internal struct whose destructor runs the `finally` code) - the same RAII mechanism [§10](10-memory-management.md) already relies on for memory, reused here for arbitrary cleanup rather than just destruction.
- **Array and string method lists made explicit, closing a real "etc." gap** ([§9](09-arrays-strings.md)): `join`, `indexOf`, `findIndex`, `some`, `every`, `unique`, `shuffle`, `binarySearch` for arrays; `startsWith`, `endsWith`, `includes`, `repeat`, `slice`/`substring`, `replaceAll`, `trimStart`/`trimEnd` for strings - each mapped to a specific STL/C++20/bundled-library backing, not left to an implementer's guess. `sort()` decided as two explicit departures from naive JS parity: a type-aware default (numeric for `number[]`, lexicographic for `string[]`, avoiding JS's own string-coercion sort footgun) and `std::stable_sort` (matching JS's stable sort, not plain `std::sort`).
- **`Object.keys(obj)`/`.values(obj)`/`.entries(obj)` added as compile-time macros** ([§8](08-variable-bindings.md)) - expanding directly to the object's known field list at compile time, not runtime reflection, so this doesn't reopen the `for...in`-on-plain-objects ban logged elsewhere in this history; it's the direct, safe resolution of "how do these JS globals work given that ban."
- **`std/network` replaces the earlier `std/fetch` + `std/server`, consolidated further and with `fetch` switched to the exact JS shape.** `fetch(url, options)` now matches real JS `fetch` exactly (no more axios-style `.get()`/`.post()`/`.custom()`), and WebSocket/`WebSocketServer` support is added alongside the HTTP server, all backed by uWebSockets internally. Full API and beta-one scope in [STDLIB-README.md](../standard-library/00-overview.md).
- **cp3 confirmed explicitly as a hosted language, not a freestanding/systems one** - every program assumes a real OS underneath (libuv needs kernel-provided `epoll`/`kqueue`/IOCP, the managed heap needs a working allocator, `import native` needs a real dynamic linker). Writing an OS kernel is explicitly out of scope, not a gap to fill later - it would need a genuinely separate freestanding compilation target, not an extension of this one ([§1](01-philosophy.md)).
- **Static linking confirmed as cp3's default build output** - every bundled library (libuv, fmt, Abseil, uWebSockets, libsodium, TBB, PCRE2, XXHash, CRC32C, Boost.Lockfree) is baked into a single executable by default, not shipped as separate shared libraries. A third-party `import native` dependency may still need dynamic linking if that's the only form the vendor ships (common for closed-source SDKs) - that's a property of the third-party library, not something cp3 works around. Full detail in [CLI-README.md §1](../cli-tooling/01-compilation-pipeline.md).

- **`parallel.*`'s capture-safety rule fixed twice over, correcting a real self-contradiction and a real data-race gap.** *(Rationale for the non-owning borrow later revised when refcounts became atomic - see the memory-model simplification entry below; the rule itself and the disjoint-index exception are unchanged.)* The rule as previously stated directly contradicted its own `parallel.for` example (which writes to a shared captured array from multiple closures - exactly what the rule said was banned), and separately missed that capturing even an *immutable* managed object still touches its non-atomic refcount from multiple threads, a genuine race independent of the data's own mutability. Fixed: closures never take a managed/refcounted handle on a capture at all - always a non-owning borrow, safe because `parallel.*` is synchronous and the calling scope's lifetime already spans the whole call (same reasoning as the native pointer safety rule, [§19](19-c-cpp-interoperability.md)); and the one named safe-write exception is writing through `parallel.for`'s own provided loop index, since distinct iterations are provably disjoint by construction - everything else stays a compile error ([§13](13-concurrency-parallel-and-workers.md)).
- **~~Escape analysis confirmed to require a genuine multi-pass compiler~~ - superseded.** Escape analysis was dropped entirely; see the memory-model simplification entry below. Kept only for the historical trail.
- **Async internals made concrete**: the "C+++ runtime" layer in the async architecture diagram is a compiler-generated Awaiter/Bridge object per suspension point, connecting `co_await` to libuv's callback model - generated automatically per std API, never written by hand. Also added **async inlining**: an `async function` that never actually suspends gets compiled down to a plain function returning an already-resolved `Promise`, skipping coroutine-frame generation entirely - a compiler optimization, not an observable semantic difference ([§14](14-async.md)).
- **`console.log`'s `Printable` reconciled with `fmt`, fixing a real inconsistency between two earlier decisions.** `console.log(...args)` compiles to a zero-cost C++ variadic template (monomorphized per call site, same mechanism as generics, [§16](16-generics.md)), not a runtime heterogeneous array. Built-in primitives route straight into `fmt` with no `toString()` call at all; user classes may implement `toString()` (an ordinary structural interface) to customize their printed form, with a default representation generated only for classes actually passed to `console.log` somewhere in the program - usage-based, the same reification approach already used for `JSON.parse<T>`, not a `toString()` proactively synthesized for every class regardless of use ([STDLIB-README.md](../standard-library/00-overview.md)).

- **Object literals against a declared type get TypeScript-style excess property checking, closing a real gap.** A fresh object literal assigned directly to a typed target (`let x: T = {...}`) is checked for fields `T` doesn't declare, not just missing ones - specifically to catch typos (`valeu` instead of `value`) that plain structural width-subtyping would otherwise silently accept as "one harmless extra field." A value already sitting in a variable and passed along afterward still gets ordinary structural checking (extra fields allowed) - same distinction TypeScript itself draws. Also closes a related question: a `class` with any `private`/`protected` field cannot be satisfied by a bare object literal at all, since there's no constructor call through which to legitimately set an inaccessible field ([§15](15-classes.md)).

- **Module resolution**: follows plain ES module semantics directly - named imports/exports are live bindings, `export * from` re-exports are supported, and circular imports between two `.cp3` files resolve the same way JS/ESM already does (a value referenced before its module finishes initializing is `undefined` at that point, not an error) - no cp3-specific deviation.
- **Cross-thread error propagation from `worker`**: `worker(...)` returns a `Promise` ([§14](14-async.md)), same as `fs.readFile`/`process.exec` - a thrown error inside a worker file simply rejects that promise, catchable with a plain `try`/`catch` around the `await`. No separate event/handle mechanism; see [§13](13-concurrency-parallel-and-workers.md) for the corrected call shape. Superseded a previous draft of this decision that used an event-based "error" handle, which didn't match `worker`'s actual (synchronous-looking, `await`-based) calling convention.
- **Native interop scope for beta one**: `import native` supports free functions and simple, non-templated, non-overloaded classes/structs where every parameter and return type is a primitive, `string`, or array/`Buffer`. Templates, function overloading on the C++ side, and operator overloading are **not supported in beta one** - this is a known, explicit limitation, not an oversight; expanding native interop coverage is post-beta-one work. (Std modules that reach native C++ internally - `fs`, `crypto`, etc. - are hand-written against this same bridge and are unaffected by this limitation, since none of them need templates/overloads to implement their documented signatures.)
- **Qt / Unreal binding surface**: explicitly **out of scope for beta one** entirely. `import "ue5"`/Qt-style bindings remain a real example of what native interop is *for* longer-term, but no specific class-by-class binding surface ships as part of beta one.
- **Generics runtime reification** (for `JSON.parse<T>`): usage-based, not universal - the compiler emits a shape descriptor (field names + type tags) only for the specific classes/interfaces that actually appear as `T` in a `JSON.parse<T>` call somewhere in the compiled program. A type that's never used with `.parse<T>` stays fully compile-time-erased, same cost as a plain C++ template - there is no blanket "all generics become reified" cost.
- **Small operator/statement confirmations**: yes to all, JS-identical - compound assignment (`+=`/`-=`/etc.), nullish/logical assignment (`??=`/`||=`/`&&=`), the exponent operator (`**`), and labeled `break`/`continue` are all in, unchanged from JS.
- **Standard library exact function signatures**: nailed down in [STDLIB-README.md](../standard-library/00-overview.md) (companion doc, updated alongside this one for beta one) - no longer just shape/examples.
- **Raw TCP/UDP socket networking beyond HTTP/WebSocket (`std/network`)**: explicitly **deferred past beta one** - not included, not partially started, don't build against it.
- **Async/await backing architecture**: C++20 coroutines (`co_await`/`co_return`), driven by a single libuv event loop - the same library backing Node's own event loop. Never exposed to cp3 code directly. Full detail and diagram in [§14](14-async.md).
- **`setTimeout`/`setInterval`/`clearTimeout`/`clearInterval` confirmed as core-language builtins, not a std import** - now with the concrete reason spelled out: they map directly onto libuv's own timer API, which is already linked the moment any program uses `async`/`await` at all, so gating them behind an import wouldn't save any linkage ([§14](14-async.md)).
- **`Promise<T>` full surface confirmed**: `.then`/`.catch`/`.finally` plus static `Promise.all`/`.race`/`.allSettled`, all built as ordinary cp3-level combinators on top of the same coroutine+libuv foundation - `await` is the primary/everyday form, but it was never meant to be the *only* one ([§14](14-async.md)).
- **Unhandled Promise rejections terminate the process** (after printing through the [CLI-README.md §2](../cli-tooling/02-error-diagnostics-source-mapping.md) diagnostics subsystem) - a stricter default than Node's historical silent-warning behavior, chosen deliberately ([§14](14-async.md)).
- **`worker` confirmed as one real OS thread per call, not a separate OS process** - cheaper to spawn, safety comes from the compiler's copy-in discipline rather than OS-level isolation; the accepted tradeoff is that a worker-thread crash can take the whole process down with it ([§13](13-concurrency-parallel-and-workers.md)).
- **`worker`'s call shape corrected to be Promise-returning** (`await worker(...)`, rejects on a thrown error) - an earlier draft of this doc had it returning an event-emitting handle, which didn't match its own documented (synchronous-looking) calling convention; fixed to match every other async std API ([§13](13-concurrency-parallel-and-workers.md)).
- **~~Managed references clarified as *not* literally `std::shared_ptr` (custom non-atomic refcount)~~ - superseded.** Managed references are now literally `std::shared_ptr` with standard atomic refcounting; see the memory-model simplification entry below.
- **Coroutine frames use the ordinary C++20 coroutine frame allocation, with reference-type locals as plain refcounted handles inside it** - not a second, separate allocation path. One memory story for the whole language ([§10](10-memory-management.md)).
- **`std/server` reinstated for beta one, superseding an earlier "removed entirely" decision.** *(Superseded further, not just here - see the `std/network` consolidation entry above, which folds this into a single module alongside `fetch`/WebSocket and switches the backend from llhttp to uWebSockets. Kept here for the historical trail.)* The original removal reasoning (avoid wrapping Drogon - too large, too template-heavy for beta-one's native-interop scope) was correct against Drogon specifically, but dropping the module entirely went too far, since it left the language's own core pitch (native-speed Express-equivalent) with nothing to demonstrate. Fixed architecture: libuv (already mandatory once `async` exists) + llhttp (Node's own HTTP parser, small and proven) + pure-cp3 routing/request/response logic - no heavy framework dependency reintroduced. `std/webview` stays dropped; nothing about this reconsideration applies to it ([§20](20-standard-library.md)).
- **`std/server` request handlers must isolate their own errors, as an explicit, deliberate carve-out from the global "unhandled rejection kills the process" rule** - still true verbatim under `std/network`'s HTTP server, just no longer under the name `std/server` specifically. One failing request must become a 500 response, not a process-level crash. Stated as a general principle (task-level isolation for any std module multiplexing independent work over one event loop), not a one-off special case ([§14](14-async.md)).
- **`std/memory`/arena concept considered and rejected.** An earlier draft proposed a `useArena((arena) => {...})` bulk-allocation module for hot-loop performance cases. Cut entirely - not deferred, not "post-beta-one," removed as a concept. If a genuine bulk-allocation need shows up later, it can be reconsidered from scratch rather than resurrected from this draft.
- **Native pointer safety rule formalized** ([§19](19-c-cpp-interoperability.md)): five concrete pointer shapes (owned / borrowed-with-length / borrowed-for-one-call / untyped `void*` / device pointers) each mapped to a specific safe wrapper pattern, plus a three-level model (safe normal language → safe advanced memory/scoped views → explicit `unsafe`). Replaces a previous one-line assertion ("native pointers are never exposed") with an actual, checkable rule.
- **Raw address access confirmed as fully absent from beta one** - no safe *or* unsafe way to read/write an arbitrary address exists yet; a future `unsafe`-gated version must use a real integer type (`r_'u64'`/`c_'uintptr_t'`) for addresses, never `number` ([§12](12-pointers-references.md), since `number` is a 64-bit double and can't exactly represent every 64-bit pointer value).
- **`mLet`/`mConst`/`mVar` considered and explicitly rejected, not just never proposed.** The idea (a "shared mutable memory cell" primitive binding, so `mLet x = 5; const y = x; x += 5;` would print `10` via `y`) is already fully achievable today with a plain object wrapper (`let x = { value: 5 }`, [§8](08-variable-bindings.md) - objects already share by reference), at zero new keywords, zero new compiler semantics, and zero added surface for every future reader of cp3 code to learn. A second family of binding keywords for a `.value`-typing savings was judged not worth the ongoing cost (type system + escape analysis + tooling + documentation, all doubled) against the "~99% JS-identical syntax" goal ([§1](01-philosophy.md)). Logged here specifically so it isn't silently re-proposed later without this context.
- **String encoding decided: UTF-8, not UTF-16** ([§9](09-arrays-strings.md), now retitled "Arrays & Strings"). A real, documented behavior difference from JS, not an implementation footnote: `str[i]` returns a raw byte (UTF-8 is variable-width, 1-4 bytes per character), and `.charAt(i)` - reusing JS's own method name - returns the actual character, walking the encoding correctly rather than doing an O(1) byte lookup. Chosen over UTF-16 for half the memory footprint on common text and 1:1 compatibility with `std::string`/native C++ APIs at every interop boundary ([§19](19-c-cpp-interoperability.md)) - the same choice Rust and Go both made for the same reasons.
- **`any` in function parameters, secretly compiled to a C++ template, considered and explicitly rejected.** The idea: let `function add(a: any, b: any)` type-check trivially in cp3 and generate a real C++ template underneath. Rejected because it reopens exactly the failure mode [CLI-README.md §2](../cli-tooling/02-error-diagnostics-source-mapping.md)'s whole diagnostics subsystem exists to prevent - `add(1, "hello")` would type-check fine in cp3, then fail inside the generated C++ template with an opaque, un-mapped instantiation error, since the cp3 frontend would have already waved the call through without knowing whether the eventual instantiation is even valid. It also directly contradicts "static typing, no `any`" ([§1](01-philosophy.md)) by reintroducing dynamic-style typing under a different name. The underlying use case is already fully solved, more safely, by generics ([§16](16-generics.md)) - `function add<T>(a: T, b: T): T` gives the same call-site flexibility with real cp3-level type-checking at the call, catching `add(1, "hello")` before any C++ is ever generated. Logged here so `any`-as-templates isn't silently re-proposed later without this context.
- **Explicitly banned JS patterns, closing a real gap**: `delete obj.prop`, adding an undeclared property to an object, `arguments`, and `for...in` on a plain object/class instance are all compile errors now, not silent gaps a JS developer would otherwise discover the hard way ([§8](08-variable-bindings.md)). This also directly resolves a previously-open question - how do plain objects work as dynamic dictionaries (TS's `{ [key: string]: T }`) - with a firm answer: they don't; `Map<K, V>` is the only supported mechanism for genuinely dynamic keys, since a cp3 object's shape is fixed at compile time the same way a C++ struct's is ([§15](15-classes.md)).
- **Confirmed explicitly: cp3's own generics compile to real C++ templates**, and this does not contradict native-interop bindgen excluding templates ([§19](19-c-cpp-interoperability.md)/[CLI-README.md §4](../cli-tooling/04-package-manager.md)) - the two are different problems. Bindgen fails on *someone else's* existing C++ templates because it has no way to know what concrete type an unfilled blueprint should be instantiated with. cp3's own generics don't have that ambiguity, because the cp3 frontend already resolved the concrete type at every call site through its own type-checking, before any C++ is emitted at all ([§16](16-generics.md)).

- **Memory-model simplification - escape analysis, non-atomic refcounts, and auto-weak all dropped ([§10](10-memory-management.md), [§11](11-reference-cycles-the-weak-keyword.md), [§12](12-pointers-references.md), [§13](13-concurrency-parallel-and-workers.md)).** After a design review, the original "escape analysis first, managed references only as a fallback" model was judged to be carrying far more machinery than the problem needed, and the spec now says:
  - **Reference types (objects, arrays, class instances, and so on) are always heap-allocated and reference-counted; value types (primitives, enums) are plain stack values.** No escape-analysis pass decides where something lives. C++ RAII (smart-pointer destructors at scope end) does all cleanup, so memory management no longer requires a whole-function analysis pass or an IR just for lifetimes. *(The compiler still needs a real type-checking frontend for structural interfaces, excess-property checks, generics, source maps and the rest - this entry is about memory management only.)* Rejected rationale for the old design: JS code shares objects so heavily that most objects would have been promoted to the heap anyway, so "stack by default" bought little for objects while costing a lot of compiler complexity.
  - **Refcounts are atomic - managed references are literally `std::shared_ptr`.** The old custom non-atomic pointer saved a few nanoseconds per operation but forced the compiler to prove no managed value ever crossed a thread boundary (including through native code, which it cannot see into). The cost was judged negligible for cp3's target workloads. Atomic counts do not make object *contents* thread-safe, so `worker` keeps its deep-copy-in rule and `parallel.*` keeps its borrow-only captures and single disjoint-index write exception ([§13](13-concurrency-parallel-and-workers.md)).
  - **Every cycle is broken by an explicit `weak`; auto-weak inference from class declaration order is gone.** The old rule silently flipped strong/weak when classes were reordered, a leak-by-refactor hazard. New syntax: a `weak` field modifier on declared fields (`weak parent: Parent`); the existing `{ weak: value }` wrapper is kept for object-literal links ([§11](11-reference-cycles-the-weak-keyword.md)).
  - **Escape analysis is not on the roadmap.** Stated like the `std/memory` and `mLet` entries: removed as a concept, not deferred. If a real allocation-cost problem shows up later, it should be reconsidered from scratch with measurements rather than resurrected from the old draft.

- **`let`/`var`/`const` confirmed non-atomic; assigning to a captured `let`/`var` inside `parallel.*` is an explicit compile error ([§13](13-concurrency-parallel-and-workers.md)).** The idea of making `let`/`var` atomic so parallel closures could update them was considered and rejected (everyone pays the cost, atomics don't make check-then-update sequences safe, and `std::atomic` can't cover strings/arrays/objects). `parallel.reduce` and the disjoint loop-index write remain the only sanctioned ways to combine or write results. Logged so it isn't silently re-proposed without this context.

- **No separate `struct`/value type - `class` is the only user-defined type, with JS reference semantics ([§10](10-memory-management.md)).** Decision: **match JavaScript.** In JS, objects are always reference types on the heap, and only primitives (`number`/`string`/`boolean`) are value types; cp3 does the same, so no `struct` keyword is added. The accepted consequence is stated plainly because it is a real tradeoff, not an oversight: a small value-like record (a point, a color, a vector) is heap-allocated and reference-counted exactly as a JS object literal would be - there is no zero-allocation, copy-semantics user type, and this is intentional JS parity, not a gap left to fill.

- **Closure-capture rule confirmed as the JS-identical, analysis-free rule ([§10](10-memory-management.md)).** A `let`/`var` captured by *any* closure lives in a shared, reference-counted cell, so the enclosing function and every closure that captured it observe the same variable - exactly like JS; `const` and never-reassigned captures are copied. It is purely syntactic (captured + reassignable → shared cell) and needs no escape analysis. This is the confirmed replacement for the dropped "promote only if the closure escapes" rule.

- **No `Atomic<T>` escape hatch - `parallel.reduce` stays the only sanctioned way to combine results ([§13](13-concurrency-parallel-and-workers.md)).** The suggestion was considered and rejected: it would reverse [§13](13-concurrency-parallel-and-workers.md)'s guarantee that cp3 never exposes locks, mutexes, or atomics to users, and atomics would not even solve the motivating case (a check-then-update sequence still races). Nothing in the spec defines it; it is explicitly not part of beta one.

- **`weak` read semantics and cycle diagnostics decided ([§11](11-reference-cycles-the-weak-keyword.md)).** Reading a `weak` field after its target has been destroyed yields `T | undefined` (the ordinary optional type; the caller narrows before use). The compiler emits a **non-fatal warning** when it can prove a reference-type cycle has no `weak` edge - a "this may leak" hint. It still never *infers* or auto-assigns `weak`; warning is not inference.
