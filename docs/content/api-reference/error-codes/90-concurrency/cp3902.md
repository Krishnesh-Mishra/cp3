# CP3902 — Parallel capture reassign

**Stage:** semantic analysis — concurrency · **Const:** `diagcode::kParallelCaptureReassign`

## What it means
A `parallel.*` closure writes to a variable captured from the enclosing scope — reassigns it, updates it (`++`/`--`, compound assignment), mutates a captured array with an in-place method (`.push`), or writes a field of a captured object — so the write happens on a pool thread against shared state.

## Why it fires
Checked by the capture-safety scan of semantic analysis, which walks every `parallel.*` closure body for writes to captured names (`src/sema/src/checks/stmt/parallel_check.cpp` + `parallel_expr_check.cpp`). The diagnostic reports `cannot reassign or mutate captured variable '<name>' inside a parallel.* closure (captures are shared, non-owning borrows); return a value and combine it on the calling thread instead`. Plain reads of captured state are allowed; only writes are rejected.

## Minimal reproducer
```ts
// fails with CP3902
let total = 0;
parallel.for(0..1000, (i) => {
  total = total + 1;
});
```
The legal form returns the per-element result and combines it on the calling thread (`parallel.reduce(0..1000, 0, (acc, i) => acc + 1)`), or declares the variable inside the closure. Pinned by `tests/cases/concurrency/parallel/capture/parallel_capture_let_reassign` and `parallel_capture_diagnostic_text` (which pins `CP3902` by name).

## What happens
Compilation stops at the front end; nothing is emitted; the diagnostic carries the code.

## How to fix
1. Return the value from the closure and combine it on the calling thread — `parallel.reduce` for a fold, `parallel.run`/`parallel.for` plus a caller-side merge for collections.
2. Move the mutated state inside the closure (create it there, use it there).
3. If shared mutable state is the point, use a worker with typed messages instead of `parallel.*` closures.
