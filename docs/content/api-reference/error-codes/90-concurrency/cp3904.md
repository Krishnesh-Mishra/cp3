# CP3904 — parallel.run result types mismatch

**Stage:** semantic analysis — concurrency · **Const:** `diagcode::kParallelRunMixedResultTypes`

## What it means
A `parallel.run(f1, ..., fN)` call mixes closures whose result types differ. `parallel.run` yields a homogeneous array, so a mixed result has no element type.

## Why it fires
Reported at the `parallel.run` call site in the compile pipeline: in this tree the emission lives in the back end's `parallel.*` lowering (`src/codegen/src/emit/misc/parallel.cpp`), and sema does not currently report it. The diagnostic reports `parallel.run() closures must all return the same type (closure <i> returns '<t>', closure <j> returns '<t>'); the result is a homogeneous array, so make every closure return one type`.

## Minimal reproducer
```ts
// fails with CP3904
import console from "std/console";
let r = parallel.run(() => 1, () => "two");
console.log(`${r}`);
```
The legal form gives every closure the same return type: `parallel.run(() => 1, () => 2)`. Pinned by `tests/cases/concurrency/parallel/run/mixed/parallel_run_mixed_result_types`.

## What happens
Compilation stops; nothing is emitted; the diagnostic carries the code.

## How to fix
1. Make every closure return one type — pick the common type explicitly, e.g. by annotating the closures or widening the returns (`(): string => "..."`).
2. If the closures genuinely produce different shapes, give them a common union return type rather than mixed naked results.
3. If the closures do different jobs, split into two calls with separate homogeneous result arrays.
