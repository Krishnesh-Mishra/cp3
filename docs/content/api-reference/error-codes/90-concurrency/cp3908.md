# CP3908 — Worker payload mismatch

**Stage:** semantic analysis — concurrency · **Const:** `diagcode::kWorkerPayloadMismatch`

## What it means
The value being sent does not match the `In`/`Out` type declared in the worker's `Thread<In, Out>` annotation. The message itself is fine as a value; it is just not this channel's message.

## Why it fires
Checked when a send is lowered (`src/codegen/src/emit/worker/worker_handles.cpp`): the argument's type is compared against the direction the annotation declares. The diagnostic reports `this message's type does not match the channel's In type (the Thread<In, Out> annotation)` (or `Out type` from the worker side). Records are compared structurally (each expected field must accept the actual field's type) and enums match by name; a plain wrong type reports the mismatch.

## Minimal reproducer
```ts
// worker_echo_impl.cp3
export default (thread: Thread<number, number>) => {
  thread.on("message", (data) => {
    thread.postMessage(data);
  });
};

// main.cp3
const w = new Worker("./worker_echo_impl.cp3");
w.postMessage("hi"); // CP3908: In is number
w.terminate();
```
The legal form sends a value of the annotated direction type (`w.postMessage(1)`). Pinned by `tests/cases/concurrency/worker/check/worker_check_payload_mismatch` and `tests/cases/concurrency/worker/channel/worker_channel_post_message_mismatch`.

## What happens
Compilation stops; nothing is emitted; the diagnostic carries the code.

## How to fix
1. Send a value of the annotated `In` (main side) / `Out` (worker side) type — the annotation is the contract.
2. If the annotation is wrong for the messages you need, change the `Thread<In, Out>` types in the entry arrow (both sides must agree; the file form reads its default export).
3. For records, narrow or widen the fields so each expected field accepts the actual field's type; enums match by name.
