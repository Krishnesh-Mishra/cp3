# CP3906 — Worker void send

**Stage:** semantic analysis — concurrency · **Const:** `diagcode::kWorkerVoidSend`

## What it means
A send targets a channel direction that is `undefined` (spells "no values"): posting a message on an `In`-empty worker from the main side, posting on an `Out`-empty worker from the worker side, or `await w.request(v)` on a worker whose `Out` direction carries nothing to reply with.

## Why it fires
Checked when the worker handle's send/request surface is lowered (`src/codegen/src/emit/worker/worker_handles.cpp`). The diagnostic reports `this worker's Out direction is empty: the main side cannot request a reply`, or `this worker's In direction is empty: the main side cannot send messages` (and the symmetric worker-side `Out` case). `undefined` in one direction of the `Thread<In, Out>` annotation means that direction is closed.

## Minimal reproducer
```ts
// fails with CP3906
const w = new Worker((thread: Thread<number, undefined>) => {
  thread.on("message", (data) => {
    console.log(`got ${data}`);
  });
});
await w.request(1);
w.terminate();
```
The legal form gives the direction a real type (`Thread<number, number>` lets `w.request(1)` return a reply), or drops the send on the `undefined` direction. Pinned by `tests/cases/concurrency/worker/check/worker_check_request_void_out` and `tests/cases/concurrency/worker/channel/worker_channel_main_void_send`.

## What happens
Compilation stops; nothing is emitted; the diagnostic carries the code.

## How to fix
1. If you want a reply, declare a real `Out` type in the annotation: `Thread<number, number>`.
2. If the worker is send-only, do not call `request` — use `postMessage` on the main side.
3. If the worker is receive-only, adjust the `In` type instead (a real `In` type makes `postMessage` legal).
