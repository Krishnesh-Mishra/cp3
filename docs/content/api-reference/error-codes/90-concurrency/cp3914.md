# CP3914 — Worker entry shape

**Stage:** semantic analysis — concurrency · **Const:** `diagcode::kWorkerEntryShape`

## What it means
The worker's entry arrow cannot be shaped the way a worker runs: it cannot be `async` (it runs once at start-up, it is not a coroutine), cannot be generic (its channel types come from the `Thread<In, Out>` annotation, so there is nothing to infer), and its single parameter must be a plain name (it is the worker-side handle).

## Why it fires
Checked when the worker entry is resolved — for the file form in the worker-unit resolution (`src/codegen/src/emit/worker/worker_module.cpp`) and for the inline form by the pre-scan at the `new Worker(...)` site (`src/codegen/src/emit/worker/worker_scan.cpp`). The diagnostics report `a worker entry cannot be async: it runs once at worker start-up and its body is the worker thread's setup` (or the inline spelling `an inline worker entry cannot be async: it runs once at worker start-up and its body is the worker thread's setup`), `a worker entry cannot be generic: the worker's channel types come from its \`Thread<In, Out>\` annotation, so there is nothing to infer a type parameter from`, and `a worker entry's parameter must be a plain name: it is the worker-side handle (\`thread: Thread<In, Out>\`)`.

## Minimal reproducer
```ts
// fails with CP3914
const w = new Worker(async (thread: Thread<number, number>) => {
  thread.on("message", (n) => {
    thread.postMessage(n);
  });
});
w.terminate();
```
The legal form uses a synchronous entry with a plain-named, annotated parameter: `new Worker((thread: Thread<number, number>) => { ... })`. Pinned by `tests/cases/concurrency/worker/check/worker_check_entry_async`.

## What happens
Compilation stops; nothing is emitted; the diagnostic carries the code.

## How to fix
1. Make the entry synchronous — do start-up work directly; use `thread.on` inside it for messages.
2. Drop the type parameters from the entry arrow; express the channel only via `Thread<In, Out>`.
3. Use a single plain-named parameter with the `Thread<...>` annotation (no destructuring or rest in the entry parameter).
