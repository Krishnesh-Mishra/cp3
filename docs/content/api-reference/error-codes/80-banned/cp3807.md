# CP3807 — Generators are unsupported

**Stage:** semantic analysis — banned patterns · **Const:** `diagcode::kGeneratorsUnsupported`

**Reserved / not currently emitted by the compiler.**

## What it means
The code slot is reserved for JavaScript generators (`function*`, `yield`). CP3 has no generators in v0.2.

## Why it fires
Never, in this tree: `diagcode::kGeneratorsUnsupported` is declared in the code table but has no emission site anywhere in `src/` or `tests/`. `yield` is tokenized (the lexer knows the keyword) but `function*` is not in the grammar, so a generator cannot be parsed into a checkable program — the construct fails earlier, in the parser. There is no sema diagnostic to reach.

## Minimal reproducer
```ts
// shape — reserved code; nothing fails with CP3807 in this build
function* gen() {
  yield 1;
}
```
The canonical situation is a `function*`/`yield` program such as the one above. Writing it today fails at the parser as an unexpected token, before semantic analysis — never with CP3807. No conformance fixture pins CP3807.

## What happens
Nothing — the code is never emitted. The generator syntax fails at parse time as a syntax error.

## How to fix
1. Nothing to fix for CP3807 — it is reserved; the parser rejects the syntax today.
2. Rewrite generators as explicit iterated loops, or return an array/`Iterable` built eagerly.
3. If you need lazy sequences, model them with a class implementing a `next()`-style API, or restructure to a `for...of` loop over a precomputed array.
