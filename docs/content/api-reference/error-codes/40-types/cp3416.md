# CP3416 — No matching overload

**Stage:** semantic analysis — types · **Const:** `diagcode::kNoMatchingOverload`

## What it means
A call to an overloaded function supplied arguments none of the declared overloads accept.

## Why it fires
When a name binds to a function-overload set (several `function` declarations in one scope, per the overloading rule in `src/sema/src/support/scopes.cpp`), overload resolution (`inferOverloadCall`, `src/sema/src/checks/call/call_check.cpp`) tests each signature for viability: parameter count and argument assignability must both fit. If no signature is viable, the call reports `no overload of '<name>' matches the supplied arguments`. A viable overload is accepted permissively (spec §17 does not yet implement full overload-dispatch typing), so an error here means none of the declared shapes matched at all. No `tests/cases/` fixture pins this code.

## Minimal reproducer
```ts
// fails with CP3416
function f(x: number): number { return x; }
function f(x: string): string { return x; }
f(true);
```
The two overloads accept `number` and `string`; a `boolean` argument fits neither, so the call reports `no overload of 'f' matches the supplied arguments`. The legal spelling passes a `number` or a `string`, or adds a `boolean` overload. This case is not pinned by a `tests/cases/` fixture; the resolution is `inferOverloadCall` in `src/sema/src/checks/call/call_check.cpp`.

## What happens
Compilation stops; nothing is produced. The diagnostic carries `CP3416` and spans the call.

## How to fix
1. Match the call to an existing overload — check argument order and count, and each parameter's type.
2. Add the missing overload to the declaration set if `boolean` is meant to be accepted.
3. If the intent was a default parameter, declare it on one signature (`function f(x: number = 0)`) rather than adding an overload purely for a shorter list — arity is checked first, then assignability.
