# CP3401 — Type mismatch

**Stage:** semantic analysis — types · **Const:** `diagcode::kTypeMismatch`

## What it means
A value of one type is used where a different type is required. This is the general type-mismatch diagnostic: the message names both sides (`cannot assign '<from>' to '<to>'`).

## Why it fires
Every assignability edge funnels through `checkAssign` (`src/sema/src/checks/expr/assignability.cpp`): initialized declarations against their annotations, arguments against parameter types, returns against return annotations, enum members, and object-literal-to-class assignments. Object shapes get a structural diff (`emitObjectDiff`) naming the mismatched property; a class with a constructor rejects a bare object literal (message: "a class with a constructor must be created with new Point(...)"); tuples check element-by-element. The native tier reports its own CP3401 flavors (strictNumericCasts refusals), and generic instantiation constraint failures at call sites report CP3401 ("type mismatch: type argument '<arg>' does not satisfy the constraint '<C>'") (`src/sema/src/checks/call/generic_check.cpp`) — annotation-position constraint failures report CP3412 instead.

## Minimal reproducer
```ts
// fails with CP3401
class Point {
  x: number;
  y: number;
  constructor(x: number, y: number) { this.x = x; this.y = y; }
}
const p: Point = { x: 1, y: 2 };
```
An object literal is not assignable to a class that declares a constructor, so the compiler reports the "must be created with new" mismatch. This exact case is pinned by `tests/cases/classes/01/class/class_literal_with_constructor` (contains: "must be created with `new Point(...)`"). The simpler everyday form — `const n: number = "five";` — reports `type mismatch: cannot assign 'string' to 'number'` through the same path.

## What happens
Compilation stops before code generation; nothing is produced. The diagnostic carries `CP3401` and spans the offending value, property or argument.

## How to fix
1. Read both types in the message: convert the value (`parseTo(x, …)`, a deliberate constructor) or change the annotation to the type you actually have.
2. For the class form, build the value with `new Point(1, 2)` instead of an object literal.
3. For tuple/array-literal mismatches, check element order and count; for property mismatches, fix the named property.
4. If the target genuinely accepts multiple shapes, write a union annotation instead of relying on a single type.
