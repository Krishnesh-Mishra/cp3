# CP3417 — Type arguments on a non-generic function

**Stage:** semantic analysis — types · **Const:** `diagcode::kTypeArgsOnNonGeneric`

## What it means
Explicit type arguments (`f<T>(…)`, `new Foo<T>(…)`) were given for a callee that declares no type parameters.

## Why it fires
`checkTypeArgs` (`src/sema/src/checks/call/generic_check.cpp`) runs on every call: a non-empty type-argument list on a callee whose signature declares no type parameters reports `type arguments are not allowed here: '<name>' is not a generic function` — only when the callee is a plain identifier (a member call like `JSON.parse<T>(…)` belongs to its own family). The same code fires for `new EventEmitter<E1, E2>()`: `EventEmitter takes at most one type argument` (`src/sema/src/checks/expr/expr_check.cpp`). If the callee is generic, no error — this code is exclusively for the callee with nothing to substitute.

## Minimal reproducer
```ts
// fails with CP3417
import console from "std/console";
function f(x: number): number { return x; }
console.log(`${f<number>(1)}`);
```
`f` declares no type parameters, so the explicit `<number>` reports `type arguments are not allowed here: 'f' is not a generic function`. The legal spelling just calls `f(1)`. This exact case is pinned by `tests/cases/generics/02/type/type_args_on_non_generic_error`.

## What happens
Compilation stops; nothing is produced. The diagnostic carries `CP3417` and spans the call.

## How to fix
1. Drop the type arguments if the callee is not generic — they have nothing to bind to.
2. If the callee *should* be generic, add the type parameter at its declaration (`function f<T>(x: T): T { return x; }`).
3. For `new EventEmitter(…)`, keep at most one type argument — the event map type — or none at all.
