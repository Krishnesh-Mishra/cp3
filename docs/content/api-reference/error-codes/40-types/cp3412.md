# CP3412 — Constraint not satisfied

**Stage:** semantic analysis — types · **Const:** `diagcode::kConstraintNotSatisfied`

## What it means
An explicit type argument does not satisfy the `extends` constraint declared on the corresponding type parameter. The instantiation is rejected.

## Why it fires
For a generic instantiation — a type alias, a generic interface, a generic class — the explicit arguments are checked against each parameter's constraint (`checkInstantiation`, `src/sema/src/checks/type/type_check.cpp`): `type argument '<arg>' does not satisfy the constraint '<C>' of type parameter '<P>' in <kind> '<name>'`. Arguments that are `unknown`/error/ambient are skipped (cascade suppression), and a type parameter satisfies unconditionally. Note the asymmetry: an out-of-line explicit type argument on a generic *function call* is checked through the plain type-mismatch diagnostic instead (CP3401, `src/sema/src/checks/call/generic_check.cpp`); CP3412 covers instantiation sites — annotations and `new` expressions — naming aliases, interfaces and classes.

## Minimal reproducer
```ts
// fails with CP3412
interface Box<T extends number> { value: T; }
const b: Box<string> = { value: "x" };
```
`string` does not extend `number`, so naming `Box<string>` reports `type argument 'string' does not satisfy the constraint 'number' of type parameter 'T' in interface 'Box'`. The legal spelling uses an argument that satisfies the constraint (`Box<number>`) or widens the constraint. This case is not pinned by a `tests/cases/` fixture; the rule is `checkInstantiation` in `src/sema/src/checks/type/type_check.cpp`.

## What happens
Compilation stops; nothing is produced. The diagnostic carries `CP3412` and spans the type argument that violates the constraint.

## How to fix
1. Pass an argument that satisfies the constraint — here `Box<number>` — or drop the constraint if it is not actually needed.
2. If the constraint is too narrow for a legitimate use, widen it (for example `T extends number | string`) at the declaration.
3. If the argument is produced by inference elsewhere, check the inferred type at the call site; an accidental `undefined` usually points at a missing initializer, not at the constraint.
