# CP3414 — Unknown type

**Stage:** semantic analysis — types · **Const:** `diagcode::kUnknownType`

## What it means
The program depends on a type the compiler cannot model — an `unknown`-sentinel value where a concrete type is required, or a native spelling the project's type system does not support.

## Why it fires
Three places report this code. (1) A value of the `unknown` sentinel type flowing into a concrete position: `value of type 'unknown' is not assignable to '<T>' without a type check` (`src/sema/src/checks/expr/assignability.cpp`), plus `property '<prop>' does not exist on type 'unknown'` / `cannot index into type 'unknown'` (`src/sema/src/checks/expr/member_check.cpp`) and the same words at the codegen fallback. (2) A native spelling that is not a known value type for the project's type system: `r_'i128'`, `r_'str'` in a rust project, `c_'long double'` in a cpp project (`src/sema/src/checks/type/type_check.cpp`, `src/sema/src/checks/type/native_types.cpp`), with the native tier's own message (for example `no portable C++ value type` / `unsized view`). Source programs cannot spell the bare `unknown` annotation — that is CP3421's diagnostic — so the sentinel subcase arises through the compiler's own untyped escape hatches (unsupported natives, permissive recovery), not through user annotations.

## Minimal reproducer
```ts
// fails with CP3414
let a: r_'i128' = 5;
```
`i128` is not a supported native type in this tree, so the annotation reports CP3414 with the native tier's message (`no portable C++ value type …`). The legal spelling names a supported native type (`r_'i64'` / `r_'u32'`) or a `number`. This exact case is pinned by `tests/cases/types/02/native/unsupported/native_unsupported_name`; `tests/cases/types/02/native/unsupported/native_unsupported_rust` pins the rust form (`r_'str'`). Source programs cannot spell the bare `unknown` annotation (that is CP3421's diagnostic), so the `unknown`-sentinel subcase arises through the compiler's own untyped values, most often from unresolved native names.

## What happens
Compilation stops; nothing is produced. The diagnostic carries `CP3414` and spans the offending annotation or expression.

## How to fix
1. For the native form, check the spelling and the project's `typeSystem`: supported value types are listed in the native-types guide; unsupported ones (i128, long double, unsized views) have no representation and must be renamed to a supported width.
2. For an `unknown`-sentinel value, narrow it before the use: an explicit type check (`typeof x === "number"`), a declared annotation, or a JSON round trip with an explicit `<T>`.
3. If the value came from an untyped library call, annotate the call site or the binding so the value has a concrete type; see [Global builtins](../../../language/99-global-builtins.md) for the ambient surface rules.
