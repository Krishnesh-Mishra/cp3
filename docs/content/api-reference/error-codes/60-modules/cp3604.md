# CP3604 — Missing default export

**Stage:** semantic analysis — modules · **Const:** `diagcode::kMissingDefaultExport`

## What it means
An import uses the default-binding form (`import d from "..."`), but the module it names has no default export.

## Why it fires
Checked when the module loader validates an import against the resolved module's export surface (`src/modules/src/support/export_surface.cpp`), right where the import is resolved. The diagnostic reports `module '<source>' has no default export`, usually with a suggestion such as `use a named import: \`import { <name> } from "<source>"\``. Not every module has a default: `std/console` does, while `std/collections` and `std/buffer` are named-only.

## Minimal reproducer
```ts
// fails with CP3604
import Collections from "std/collections";
const m = new Collections.Map();
```
The legal form uses the named import: `import { Map } from "std/collections";`. No conformance fixture pins CP3604 in this tree; the shape follows the import-validation path in `export_surface.cpp`.

## What happens
Compilation stops at the front end; nothing is emitted; the diagnostic carries the code.

## How to fix
1. Use the named import listed in the suggestions: `import { Map } from "std/collections";` (check [the module guide](../../../language/06-modules-and-errors/01-modules.md) for the exact export list).
2. If you meant a different module, verify the specifier — you may be importing the wrong unit.
3. If you own the module, add a default export, or document the named-only surface.
