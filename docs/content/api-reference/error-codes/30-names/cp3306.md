# CP3306 — Undefined label

**Stage:** semantic analysis — names · **Const:** `diagcode::kUndefinedLabel`

## What it means
A `break` or `continue` names a label that does not enclose it. The statement would jump nowhere, so it is rejected.

## Why it fires
Label scope is dynamic: labels are registered as loops and blocks are entered (`visitLabeled` / `labels_` in `src/sema/src/checks/stmt/stmt_check.cpp`) and checked at the `break`/`continue` site. A `break` to a label outside the current statement list reports `undefined label '<label>'`; the same check backs `continue`. A label that *exists* but sits on a non-iteration statement is legal for `break` but not for `continue` — that is `kContinueNonIterationLabel` (CP3508), not this code. Code generation repeats the check so a bad label never reaches C++ (`src/codegen/src/emit/control/control.cpp`).

## Minimal reproducer
```ts
// fails with CP3306
for (const x of [1, 2, 3]) {
  break missing;
}
```
No `missing:` label encloses the loop, so the compiler reports `undefined label 'missing'`. The legal form either labels the loop (`outer: for (…) { break outer; }`) or uses a bare `break`/`continue`. This case is not pinned by a `tests/cases/` fixture; the check is `visitBreak`/`visitContinue` in `src/sema/src/checks/stmt/stmt_check.cpp`.

## What happens
Compilation stops; nothing is produced. The diagnostic carries `CP3306` and spans the `break`/`continue` statement.

## How to fix
1. If you intended to target the enclosing loop, drop the label: bare `break`/`continue` bind to the innermost loop or switch.
2. If you intended an outer loop, label it at the statement (`outer: for (…) { … }`) and make sure the `break`/`continue` is lexically inside it.
3. Check for a typo in the label, and for the label being declared after the jump statement — labels bind only to statements that follow them.
