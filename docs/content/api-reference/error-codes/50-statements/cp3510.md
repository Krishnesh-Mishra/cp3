# CP3510 — Return in finally is ignored

**Stage:** semantic analysis — statements (warning) · **Const:** `diagcode::kFinallyReturnIgnored`

## What it means
A `return` with a value inside a `finally` block does not override the pending completion, unlike JS/TS where `finally` wins. CP3 runs the `finally` block on exit and then lets the pending `return`/`catch` completion proceed — the `return`'s value is ignored.

## Why it fires
Checked in the statement pass of semantic analysis, which tracks whether the surrounding block is a `finally` body of a `try`/`try-catch`. The diagnostic reports `in TS/JS, \`return\` inside \`finally\` overrides a pending return/catch completion; in cp3 the value is ignored -- the \`finally\` block runs on exit, then the pending completion proceeds`. It is a warning: the behavior is defined, the value is just dropped.

## Minimal reproducer
```ts
// warns with CP3510
import console from "std/console";
function f(): number {
  try {
    return 1;
  } finally {
    return 2; // ignored in cp3; JS would return 2
  }
}
console.log(`${f()}`); // prints 1
```
The legal form does the work that needs the value inside `try`/`catch`, and keeps `finally` for cleanup only — no conformance fixture pins CP3510 in this tree; the shape follows `tests/cases/errors/01/finally/finally_before_return_value` and the rule pinned in `tests/cases/AMBIGUITIES.md`.

## What happens
Compilation continues; the diagnostic carries the code as a warning. The emitted program returns the pending value (`1` in the example), not the `finally` value.

## How to fix
1. Move the value you want returned out of `finally` — compute it in the pending completion, not in the `finally` body.
2. Keep `finally` for cleanup only (release, close, reset), which is what the language expects to find there.
3. If you actually want the `finally` to decide the result, return from the `try`/`catch` paths instead of the `finally`.
