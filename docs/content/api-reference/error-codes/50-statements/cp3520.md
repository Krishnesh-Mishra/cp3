# CP3520 — Loose equality with a nullish literal

**Stage:** semantic analysis — statements (warning) · **Const:** `diagcode::kLooseEqualityNullish`

## What it means
A comparison against `null` or `undefined` uses loose `==`/`!=`. CP3 matches only the same flavor of nullish value (`null == undefined` is `false`), so the JS habit of `x == null` does not do what it does in JS/TS here.

## Why it fires
Checked in the operator-checking pass of semantic analysis, which flags a loose `==`/`!=` when either side is a `null` or `undefined` literal. The diagnostic reports `comparing against a nullish literal (\`null\` or \`undefined\`) with \`==\`: cp3 matches only the same flavor (null == undefined is false; JS coerces them); use === for a literal check`. It is a warning because the program is well-typed; the comparison is just not what JS programmers expect.

## Minimal reproducer
```ts
// warns with CP3520
import console from "std/console";
function f(x: number | undefined): boolean {
  if (x == undefined) {
    return true;
  }
  return false;
}
console.log(f(undefined));
```
The legal form uses `===` for the literal check, or the language's nullish-handling sugar if you need "either flavor" semantics. No conformance fixture pins CP3520 in this tree; the shape follows the operator-check in `src/sema/src/checks/expr/ops_check.cpp`.

## What happens
Compilation continues; the diagnostic carries the code as a warning. The comparison keeps its same-flavor semantics.

## How to fix
1. Use `x === undefined` (or `x === null`) when you mean a specific flavor — that is what the check is asking for.
2. If you truly want "either flavor", write the disjunction explicitly (`x === undefined || x === null`), or use the language's nullish check where available.
3. If the operand is not actually nullable, drop the comparison.
