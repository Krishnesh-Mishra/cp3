# CP3208 — JSON.parse missing a type argument

**Stage:** parser · **Const:** `diagcode::kJsonParseMissingTypeArgument`

## What it means
`JSON.parse` (and the sibling `JSON.parseFile` / `JSON.parseFileSync` / `JSON.verify`) were called without an explicit type argument. The value type is unknowable without it, so the call is rejected instead of silently producing an untyped value.

## Why it fires
An interim parser-side check flags a bare `JSON.parse(...)` — no `<T>` anywhere in the call, not even an empty `<>` (`src/parser/src/expr/primary.cpp`, via `isBareJsonParse`). A dedicated sema-side check reports the same code for calls that reach analysis, including the file-based variants (`src/sema/src/checks/call/call_check.cpp`), with the message `JSON.parse requires a type argument; use JSON.parse<T>(x)` (or the analogous wording for `verify` / `parseFile` / `parseFileSync`). The parser prefixes its form with `syntax error: `. The result the compiler would otherwise have to invent is exactly the value you must name.

## Minimal reproducer
```ts
// fails with CP3208
import JSON from "std/json";
const v = JSON.parse("1");
console.log(v);
```
The bare call has no type argument, so the compiler rejects it instead of guessing. The legal spelling states the expected value type: `JSON.parse<number>("1")`, `JSON.parse<Config>(text)`, … This exact case is pinned by `tests/cases/v0-2-2/json_parse_untyped`, and `tests/cases/stdlib/02/json/parse/untyped/json_parse_untyped_field_needs_narrow` pins the same for field access. See [JSON](../../../standard-library/09-json.md).

## What happens
Compilation stops before semantic analysis; nothing is produced. The diagnostic carries `CP3208` and spans the call.

## How to fix
1. Add the type argument: `JSON.parse<T>(text)` where `T` is the shape the JSON must have — an interface you declare, or an inline object annotation.
2. If you only want to test well-formedness, use `JSON.verify<T>(text)` — it is also type-argument-required and returns `boolean`.
3. Parse first, then validate: cp3 does not infer a shape from the payload, so domain validation after parsing is still your job.
