# CP3 v0.2.6 — native engine backends, type queries, source packages

CP3 is a statically typed language with familiar TypeScript-shaped syntax that compiles ahead of time to native executables. v0.2.6 is the **native-backend and type-level wave**: JSON parsing and serialization, `parallel.*` and `Queue<T>` now ride pinned vendored engines (simdjson, glaze, oneTBB, moodycamel), TypeScript type queries and utility types land with closed-world enforcement, `.cp3pak` becomes a source package under a clean-break format, and the compiler and generated programs move to C++23.

> **Beta:** CP3 and its standard library are under active development. Check the repository documentation and the benchmark methodology before relying on feature semantics or comparing performance results.

## What's new

### Native engines behind JSON, `parallel.*` and `Queue<T>`

Four pinned, static-vendored C++ libraries are now the direct backends for surfaces that used to be hand-written. Public CP3 APIs and diagnostics are unchanged, and generated code never names these libraries directly:

- **`parallel.for` / `parallel.reduce` / `parallel.run`** schedule through vendored **oneTBB v2023.1.0**. Chunk scheduling, capacity handling and the single-threaded fallback when the parallel flag is off all live in the engine; `-ltbb`/`-pthread` are linked only for programs that name the parallel surface (the `core/parallel` native row). The Worker/Channel message-passing layer keeps its existing FIFO, drop-on-close machinery.
- **`Queue<T>`** is backed by vendored **moodycamel concurrentqueue v1.0.4** — MPMC-safe enqueue/dequeue with exact `length()` semantics through an atomic counter (not `size_approx`), a single-slot head cache for `peek`, and `clear()` that drains through dequeue so the count stays consistent. The other collection surfaces are unchanged.
- **`JSON.parse<T>`** routes its public hot path through vendored **simdjson v5.1.1** — the DOM scanner and number bytes are the engine's; the record/array builders remain CP3's. On engine failure (duplicate key, dialect edge case) the recursive-descent reader re-derives the result with canonical `ParseError` offsets. `JSON.parseFile`/`parseFileSync` and `verify<T>` ride the same path, including a define that preserves `-0`.
- **`JSON.stringify`** routes through vendored **glaze v9.1.0** (`glz::to<glz::JSON, ...>`), while number spellings, control-character escapes and indent/gap layout remain hand-written, so output stays byte-identical. Only glaze's JSON serializer is used; CSV/CBOR/BSON and the rest are excluded.

Because generated programs compile the engine translation units they need, existing programs should be rebuilt against the new tree.

### Type-level queries and utility types

The analyzer now understands the TypeScript type-query family, resolved entirely at compile time with zero runtime emission:

- `typeof <entity>` in **type position** (`type Config = typeof config`). Value-position `typeof` is unchanged.
- `keyof T` as a union of string-literal keys, and `T[K]` indexed access (union keys distribute; `K` must be a subtype of `keyof T`).
- Utility types `Parameters<F>`, `ReturnType<F>`, `ConstructorParameters<C>`, `InstanceType<C>` and `Awaited<T>` (recursive unwrap; non-`Promise` passes through).
- `expr as const`: literal preservation (the D51 widening is suppressed), and object-member mutation is rejected.

`keyof` and `T[K]` resolve only over closed shapes — an `interface`, a `class`, a `type` alias, or an exact object literal. Open shapes (`object`, `unknown`, an open index signature) fail with diagnostics in the `CP3620`–`CP3625` family; every message carries the word `closed`, and there is no `any` fallback. The docs page [Generics](../language/05-generics/01-generics.md#type-level-queries) has the full surface with examples. Pins live under `tests/cases/v0-2-6/types/`.

### `.cp3pak` is now a source package (formatVersion 2)

A multi-module package used to pack a generated `index.cp3` signatures stub whose relative imports pointed at modules that were never shipped, so a consumer failed with `CP3601` and `CP3302`. `cp3c build` now packs:

- the entry's **relative-import closure** as plain `.cp3` sources at their package-relative paths (the exact source folder structure),
- `package.json` verbatim,
- `cp3pak.json` with `formatVersion: 2` and `main` as authored,
- native members and `build.files`, when present.

There is no signatures stub, no compiled members and no binary cache (`build.cacheBinary` is ignored with a warning). Install extracts the same layout, and the consumer compiles the package sources like ordinary units — so the same `.cp3pak` works on any target platform. Directory installs materialize the same layout instead of compiling at install time; `cp3 recompile` reports that new-format paks carry no C++ source.

This is a **clean break**: `formatVersion` other than 2 is rejected at every install/link path with `unsupported .cp3pak formatVersion` / `rebuild the package with a newer cp3c`, and nothing is extracted. An import escaping the package root fails the pack with `escapes the package root` and produces no `.cp3pak`.

For a local package file, `cp3 install <file.cp3pak>` now asks on an interactive terminal (default **No**) whether to delete the source file after a successful install. Non-TTY runs and `--json` never prompt and never delete; failures never delete.

Docs: [Packages and `.cp3pak`](../cli-and-compiler/12-packages.md). End-to-end pins: `tests/cases/v0-2-6/package-e2e/`.

### C++23 is the language floor

CP3 now builds itself and generated programs with **C++23** (`-std=c++23`). The floor is required by the vendored glaze and oneTBB headers and by the simdjson parse translation unit. The toolchain cache key carries `std:c++23`, so D34 object reuse cannot accept a stale precompiled header built under the old standard — the mismatch invalidates the PCH automatically instead of surfacing as a confusing Clang error. Build with a compiler that supports C++23 (`g++` 13+ or a current Clang).

### Test harness: retry only transient failures

`run_tests.py` used to rerun every failing case three times with a cold `.cp3`, including deterministic compiler diagnostics. Each retry rebuilt the runtime mirror and PCH, and a handful of known-red fixtures could stall the corpus for hours. Retries now apply only to run-mode failures that did not fail the C++ compile step; check-mode and deterministic compile failures are reported once. Stale-intermediate and load-related failures still get the three-tier retry.

## What was fixed

- **Multi-module `.cp3pak` packages are installable again.** The entry's relative-import closure ships at its authored paths, so consumers no longer hit `CP3601` on the stub's imports or `CP3302` on the types behind them.
- **Package-import linking** now comments/handles Package-resolution units like local modules (ordinary C++ namespaces), closing the missed hunk from the format change.
- **Release packages stage oneTBB for `parallel.*`.** Both packagers now collect every core backend row (PCRE2 and oneTBB) and keep only the target architecture's archive, so a parallel program links from the installed tree instead of failing on a missing TBB archive.
- **Stale PCHs are invalidated when the language standard changes**, instead of being accepted and then rejected by Clang.
- **`Queue<T>.length()` is exact** in sequential execution and never undercounts or wraps under concurrency, despite moodycamel exposing only an approximate size.
- **`JSON.parse<number>("-0")` preserves the negative zero** through the simdjson path.

## What changed behaviorally

- **Old `.cp3pak` files no longer install.** Packages built through v0.2.5 (`formatVersion: 1`) must be rebuilt and republished with v0.2.6.
- **C++23 is required** for the compiler build and for every program CP3 compiles. A compiler that cannot accept `-std=c++23` is not usable with this release.
- **Programs should be rebuilt.** The `Queue<T>` backing type changed in the public header, and the JSON/parallel engine translation units are new.
- **`build.cacheBinary` is ignored** (with a warning); the source-package format ships no binary cache.
- **Linux x64 and Windows x64 ship oneTBB archives.** Other targets have no parallel archive yet.

## What is still open

- Conditional and mapped types, and higher-kinded types, are not available; the type-query surface is the closed-world subset described above.
- The oneTBB archive set covers Windows x64 and Linux x64. Linux arm64/darwin have no `parallel.*` archive yet; the native row reports a clear "no vendor archives for target" diagnostic instead of mislinking.
- The package end-to-end suite's interactive delete prompt cannot be exercised by the scenario harness (non-TTY paths are pinned; the prompt itself is documented for manual verification).
- This release's asset set contains the Linux x64 package only; the Windows MSI is not published with this tag.
