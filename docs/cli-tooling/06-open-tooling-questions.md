# 6. Open tooling questions

**Resolved since the initial draft** (kept here for history, tooling/CLI/package-manager decisions only - see the language spec's own history for everything else): `.cp3pak` internals (compressed C++ source + auto-generated `index.cp3`, not a compiled binary by default) · optional per-platform binary cache (`cacheBinary` + `cp3 recompile`) · `cp3 init` workflow (now 4 questions, including type-system pattern) · arrays explicitly confirmed homogeneous by default, mixed types require an explicit union - not "free" just because vectors are used underneath ([README.md §9](../language-spec/09-arrays-strings.md)) · compiler build architecture (`.build/` persistent incremental output directory mirroring project structure, one `.cpp`/`.hpp` pair per `.cp3` file - never one flat `main.cpp` - fixed per-platform toolchain order: MSVC→Clang→GCC on Windows, Apple Clang→Clang→GCC on macOS, Clang→GCC on Linux, with silent fallback retry on failure) · error diagnostics as a first-class subsystem (source-mapped, cp3-native error messages instead of raw C++ compiler output; step-based build progress, not a percentage bar, with the step count growing on toolchain fallback; multi-toolchain failures grouped by same-vs-different underlying error, [§2](02-error-diagnostics-source-mapping.md)) · prelude file stacking order for multiple files in one folder (`_prelude.same.cp3` → `_prelude.cp3` → `_prelude.weak.cp3`, [README.md §18](../language-spec/18-modules-imports.md); strong + weak coexisting in one folder confirmed as allowed, not a conflict - each follows its own independent rule) · **compiler implementation language decided: C++**, not TypeScript or another host language - dogfooding, and consistent with the project's own no-GC/no-bundled-runtime performance stance · **internal library wrapping specified**: Abseil (optional faster `Map`/`Set` backend), fmt (`console.log`/string formatting backend), XXHash (internal hashing), CRC32C (`.cp3pak`/`.build` cache integrity checks), Boost.Lockfree/libcds (internal lock-free runtime queues only, never a user-facing concept) - same "wrap proven C++ libraries invisibly" pattern as libsodium/TBB, [README.md §20](../language-spec/20-standard-library.md).

**Resolved for beta one** (closing out items that were previously open - tooling/CLI/package-manager decisions; see [README.md](../language-spec/00-overview.md)'s own history for language decisions):

- **CLI surface confirmed sufficient for beta one, plus three additions**: `cp3 --version`/`cp3 version`, `cp3 clean` (wipes `.cp3/build/`; `--all` additionally wipes `.cp3/packages/`), and `cp3 exec <package> [args]` ([§1](01-compilation-pipeline.md)) - a **confirmed exception**, not a reopening of the general question. `cp3 exec` is required because `"type": "package"` ([§5](05-package-format-authoring-cp3pak.md)) has no runnable output at all, which blocks any package (`cp3ui` being the first real one, `CP3UI-README.md`) that needs to ship a build-time tool rather than only a library. It's implemented as existing pieces (`cp3 install`'s resolution, `cp3 run`'s build-and-execute, `.cp3/build/`'s cache pattern) pointed at a dependency's new `"bin"` field ([§5.1](05-package-format-authoring-cp3pak.md)), not a new subsystem. `cp3 upgrade`/`cp3 config`/`cp3 profile` and similar stay explicitly post-beta-one, as does the `npx`-style fetch-and-run-without-installing form of `cp3 exec` (roadmap, above) - no known beta-one package needs it.
- **`package.json` lifecycle script hooks confirmed for beta one**: a script named `pre<name>`/`post<name>` runs automatically immediately before/after the script or built-in command named `<name>` (npm's own convention, adopted as-is) - e.g. a `"prebuild"` script runs before `cp3 build`. This is what lets `cp3 exec cp3ui transform` (above) wire itself into an ordinary build with one `package.json` line, with no new compiler or CLI mechanism beyond the hook-naming convention itself.
- **`--max-memory` flag added for `cp3 build`/`cp3 run`** - caps codegen-phase RAM usage (absolute MB or a percentage of system RAM), defaulting to 70% of system RAM so a large project can't accidentally OOM the machine building it. A build that would exceed the cap processes files in smaller sequential batches rather than failing outright.
- **Static linking confirmed as the default build output, with a documented exception for third-party native dependencies, and `bundleNativeDlls` added to automate the exception.** cp3's own bundled libraries are always statically linked. A dynamically-linked `import native` dependency needs its shared library present on the machine running the final executable - `"build.bundleNativeDlls"` (default `true`) automates copying it into the output folder at build time, cross-platform (`.dll`/`.so`/`.dylib`, auto-detected). Full detail in [§1](01-compilation-pipeline.md) and [§5.1](05-package-format-authoring-cp3pak.md).
- **Build strategies and toolchain acquisition confirmed for beta one** ([§1](01-compilation-pipeline.md)). `cp3 build`/`cp3 run` are **incremental** by default: they reuse the cached object files in `.cp3/build/`, recompile only the `.cp3` files that changed, and link - each translation unit compiled with the toolchain's optimized setting (`-O2`/`/O2`), though without cross-file context. **`cp3 build --release`** compiles everything from scratch and links with **LTO** for whole-program optimization (the ship build); **`cp3 build --debug`** gives `-O0`/`/Od` plus debug symbols. LTO is therefore **in beta one**, scoped to `--release` - the fast incremental default deliberately does not enable it. The C++ toolchain used is the **system** one (fixed per-platform order, silent fallback, **Toolchain detection** above), never a bundled or pinned compiler; when none is found, `cp3` offers to download Clang rather than failing. cp3 **never uses CMake** - it drives the compiler driver directly.
- **`std/network`'s server/WebSocket backend switched from llhttp to uWebSockets**, superseding the earlier llhttp-based `std/server` decision - uWebSockets already includes its own HTTP parsing and handles WebSocket framing/handshake in the same event loop, making a separate HTTP parser redundant once the server backend itself changed. Internal library table ([§3](03-internal-library-wrapping.md)) updated accordingly.
- **A large set of Phase 2/3 compiler-engineering and DX ideas (LSP, debugger, loop fusion, refcount elision, bounds-check elimination, safe auto-parallelization, whole-program tree shaking, incremental frontend caching, and more) explicitly deferred past beta one, at the project's own direction** - captured as a documented roadmap (above) rather than either silently dropped or accidentally treated as beta-one requirements. One item confirmed to need no engineering at all, ever: liveness-based "early drop" - C++'s own RAII plus the C++ compiler's own optimizer already handle this correctly without any manual cp3-compiler pass.

- **`.cp3pak`'s compression scope clarified - a real ambiguity, not just a wording nitpick.** The layout-once-installed diagram previously showed the on-disk `pak/*.cpp`/`*.hpp` files as "highly compressed," which could be misread as "the compiler decompresses on every build." Fixed: compression exists only in the single downloadable `.cp3pak` archive, for the network transfer; `cp3 install` decompresses it exactly once, and `cp3 build` reads plain, ordinary files off disk like any other C++ source, no decompression step involved, ever ([§5](05-package-format-authoring-cp3pak.md)).

- **Error report format** ([§2](02-error-diagnostics-source-mapping.md)): static, well-formatted printed report - not a live TUI - for beta one; see [§2](02-error-diagnostics-source-mapping.md) for the decision and reasoning.
- **Error diagnostics coverage** ([§2](02-error-diagnostics-source-mapping.md)): minimum required category list specified directly in [§2](02-error-diagnostics-source-mapping.md), with a labeled generic fallback for everything else.
- **`.cp3pak` compression & versioning**: gzip-compressed archive; a manifest header inside the pak carries an integer `formatVersion` field, incremented only when the `.cp3pak` container format itself changes - independent of, and unrelated to, the package's own semver `version`.
- **Debugger / LSP / IDE tooling**: explicitly **out of scope for beta one**. Beta one is compiler + std lib + CLI only; tooling is a deliberate follow-on, not a hidden dependency of beta one shipping.
- **C++ standard floor raised to C++20**, specifically for coroutine support - was previously unspecified anywhere in this doc. Not C++23; the smallest standard that makes coroutines work, on purpose ([§1](01-compilation-pipeline.md)).
- **`libuv` added to the internal-library wrapping table** ([§3](03-internal-library-wrapping.md)), alongside libsodium/TBB/fmt/etc. - same "wrap it invisibly, never expose it" pattern.
- **Offline bindgen tool added for native interop (`cp3 native-install`)**, superseding the earlier "cp3 blindly transpiles native calls, C++ compiler catches mismatches" model as the primary path. Bundles **libclang** (parsing library only, not the full compiler - same approach as Rust's own `bindgen`) to parse a native library's headers once, offline, generating a `.cp3/native/<lib>/index.cp3` declaration file the cp3 frontend type-checks native calls against directly - turning native-interop mismatches into ordinary cp3 type errors instead of opaque C++ template walls, and giving native calls real editor autocomplete for free, since the generated file is ordinary `.cp3` syntax. Full detail in [§4](04-package-manager.md). **This narrows, but does not remove, the error-diagnostics subsystem's job ([§2](02-error-diagnostics-source-mapping.md))** - that subsystem still exists for cp3-frontend compiler bugs and opaque errors from cp3's own generated code (variant/coroutine internals), neither of which bindgen touches; only the native-interop slice of its original scope goes away. A real, documented limitation: a header's type signature alone can't say whether a returned pointer is owned or borrowed, so bindgen fully automates simple value types but may need a binding author to manually classify pointer-returning functions into the native pointer safety table ([README.md §19](../language-spec/19-c-cpp-interoperability.md)).
- **Project tooling layout consolidated into one hidden `.cp3/` directory** (`.cp3/packages/`, `.cp3/native/`, `.cp3/build/`, `.cp3/lock.json`), replacing the earlier scattered `.packages/`/`.build/`/`cp3.lock` at the project root. Pure tooling/UX change, not a language-semantics one - cleaner root, a single `.gitignore` entry, faster IDE indexing since generated C++ and full native headers never need to be indexed at all.
- **`cp3 install` accepts a public GitHub repo URL directly**, checking the repo's latest non-prerelease release for `.cp3pak` assets: one match installs directly, multiple prompt an interactive selector, none produces a clear named error. Recorded in `.cp3/lock.json` with repo, tag, filename, and a SHA256 hash pinned at install time - since a GitHub release isn't a curated, integrity-guaranteed registry the way the normal `.cp3pak` install path is, pinning the hash lets a later install/CI run detect if a tag's asset silently changed. Scoped to GitHub specifically for beta one, not a generic git-URL feature.
- **`cp3 install <github-url>` refined with `--auto` compatibility selection**: when a release has multiple `.cp3pak` assets, `--auto` picks the one whose `package.json` `"engines.cp3"` range matches the installed compiler, falling back to the interactive selector rather than guessing if the result is still ambiguous or no candidate declares `"engines"` at all. `"engines"` added as a new optional `package.json` field ([§5.1](05-package-format-authoring-cp3pak.md)).
- **`excludeSource` added as an explicit, opt-in exception to the "a `.cp3pak` always carries its C++ source" default** ([§5.4](05-package-format-authoring-cp3pak.md)) - for authors who've already committed to `cacheBinary` covering their target platforms and don't want to ship dead-weight source nobody will compile. Requires at least one `cacheBinary` platform (a `cp3 build`-time validation error otherwise, since an empty list would make the package permanently uninstallable for everyone) and never excludes `index.cp3` (still needed for IDE autocomplete/type-checking regardless). The real, accepted cost - a platform outside the author's `cacheBinary` list has zero fallback for that package - is surfaced as a clear, specific install-time error, not a raw linker failure.
- **CLI command surface formalized**: `cp3 run` (build+execute in one step), `cp3 check` (frontend-only type-check, no C++ generation/invocation/linking - fast because the C++ toolchain step is what's actually slow, not cp3's own frontend), `cp3 dev` (incremental watch mode), `cp3 fmt` (zero-config formatter, `package.json`-overridable). `cp3 init` now generates standard `dev`/`build`/`start`/`check` `package.json` scripts by default. A standalone `cp3 doctor` is deprioritized - toolchain detection is already mandatory and automatic on `init`/`build`/`run` ([§1](01-compilation-pipeline.md)), so a separate on-demand version of the same check isn't a beta-one requirement.
- **"Dual-runtime" dev-mode approach (a JIT/interpreter like Cling for fast iteration, compiled C++ for production) considered and explicitly rejected**, logged here so it isn't silently re-proposed later without this context: two different execution engines for the same program guarantees eventual semantic divergence - `import native` has no straightforward path through an interpreter, cp3's specific ARC + RAII + explicit-`weak` memory model ([README.md §10](../language-spec/10-memory-management.md)/[README.md §11](../language-spec/11-reference-cycles-the-weak-keyword.md)) would need to be perfectly replicated by a second engine or bugs only manifest in production, and interpreted vs. optimized-compiled floating-point/UB behavior isn't guaranteed identical. The actual fix for `cp3 dev`'s speed goal needs none of that risk: surgical incremental recompilation (one `.cpp`/`.hpp` pair per `.cp3` file, [§1](01-compilation-pipeline.md), plus the persistent `.cp3/build/` cache) paired with a fast linker - same backend in dev and prod, zero divergence risk ([§1](01-compilation-pipeline.md)).
- **Runtime crash reporting added as a distinct, much lighter subsystem from compile-time diagnostics** ([§2](02-error-diagnostics-source-mapping.md)): an embedded `.cp3`-to-`.cpp` line-number source map (the same source-map concept already required for compile-time mapping, [§2](02-error-diagnostics-source-mapping.md)) lets a runtime crash print a `.cp3` file/line instead of a raw address or generated-C++ location. A lookup-table read, not a translation system - doesn't require anywhere near the scope of the compile-time error mapper.
- **"Did you mean...?" typo suggestions added to diagnostics** ([§2](02-error-diagnostics-source-mapping.md)): Levenshtein-distance-style matching against in-scope names, appended to "does not exist" errors. Cheap, standard practice (TypeScript, Rust), logged as confirmed for beta one.
- **CLI spinner rule confirmed**: any command over ~0.5s gets a spinner/progress indicator; anything faster shows nothing, since a spinner on a near-instant command reads as a glitch rather than useful feedback ([§1](01-compilation-pipeline.md)).
- **Pre-existing section-numbering bug fixed, unrelated to any new decision**: [§5](05-package-format-authoring-cp3pak.md)'s subsections were mislabeled `21.1`-`21.6` (matching an old section-21 numbering that predates this doc's current section order), and two internal cross-references pointed at nonexistent `§25.3`/`§25.4`. After this document's own subsequent split into [README.md](../language-spec/00-overview.md) and [CLI-README.md](00-overview.md), that section is now `[§5](05-package-format-authoring-cp3pak.md)` here, so those subsections are `5.1`-`5.6` and the fixed cross-references are `[§5.3](05-package-format-authoring-cp3pak.md)`/`[§5.4](05-package-format-authoring-cp3pak.md)` - worth a note here since a stale cross-reference is exactly the kind of ambiguity that costs an implementer real time chasing a section that doesn't say what it's pointed at.
- **Regex engine decided: PCRE2**, not `std::regex` (slow, missing some JS regex features) and not RE2 (faster and ReDoS-resistant, but no backreferences, so it can't give full JS parity). Adds roughly 150-300KB to a final binary. Added to the internal library wrapping table ([§3](03-internal-library-wrapping.md)) - same "wrap it invisibly" pattern as every other bundled library.
- **Qt clarified as failing on MOC specifically, not merely on the templates/operator-overloading gap** - even a bindgen that fully supported both would still fail on `Q_OBJECT`/`signals:`/`slots:`, since those aren't parseable C++ at all until Qt's own MOC tool generates code from them first, which happens outside anything `libclang`-based bindgen can see. **Confirmed direction: a hand-authored `.cp3pak` Qt bridge, post-beta-one, owned by the project, not a future bindgen capability.** Full reasoning and scope in the roadmap section above.

**Still genuinely open / not required for beta one** (implementation-detail engineering, not spec gaps):

- [ ] Compiler implementation architecture itself (transpiler internals, IR if any, pass structure) - this is the actual engineering work of beta one, not a design decision blocking it.

**Guiding principle:** define C+++ semantics independently first, and treat C++ as *only* the initial implementation backend - this keeps the language decoupled from C++'s complexity while still reusing its mature, battle-tested compiler infrastructure. For the full set of core language decisions (types, memory model, concurrency, classes, etc.), see [README.md](../language-spec/00-overview.md).
