# 3. Internal library wrapping

Several std modules and internal runtime pieces are backed by established, high-performance C++ libraries - never exposed directly; the user only ever sees cp3's own API surface. Same pattern already established for `crypto` (libsodium) and `parallel.*` (TBB, [README.md §13](../language-spec/13-concurrency-parallel-and-workers.md)), extended to a few more pieces:

| Library            | Used for                                                                                                                                        | Where it surfaces to the user                                                                                                               |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **Abseil**         | `flat_hash_map`/`InlinedVector` as an optional faster backend for `Map`/`Set`/internal containers, plus string utilities, synchronization, time | `std/collections`' `Map`/`Set` API stays identical whether backed by `std::unordered_map` or Abseil's `flat_hash_map`; also backs `string.replaceAll`/`.trimStart`/`.trimEnd` ([README.md §9](../language-spec/09-arrays-strings.md))    |
| **fmt**            | Fast, safe string formatting                                                                                                                    | Backend for `console.log` and string interpolation - user sees `console.log(...)`, never `fmt::format`                                      |
| **libuv**          | Single-threaded event loop: timers, async file/process I/O, background thread pool for blocking work                                          | Backend for `async`/`await`, `setTimeout`/`setInterval`/`clearTimeout`/`clearInterval`, and every Promise-returning std call (`fs`, `fetch`, `process`, `worker`) - user sees `await`/`Promise`/`setTimeout`, never a libuv handle or callback directly ([README.md §14](../language-spec/14-async.md)) |
| **uWebSockets** (uWS, built on uSockets) | HTTP parsing/routing and WebSocket framing/handshake, in one C++ library, sharing a single event loop | Backend for `std/network`'s HTTP server and `WebSocket`/`WebSocketServer` - user sees `app.get(...)`/`res.json(...)`/`ws.on("message", ...)`, never uWebSockets directly. Superseded llhttp: since uWebSockets already has its own HTTP parsing built in, a separate parser is redundant once the server backend switched |
| **PCRE2**           | Regex engine with full JS regex feature parity (lookaheads, lookbehinds, backreferences)                                                        | Backend for native `/pattern/flags` regex literals (mentioned as a core-language builtin needing no import, [README.md §20](../language-spec/20-standard-library.md) above) - chosen over `std::regex` (notoriously slow, and missing some JS regex features) and over RE2 (faster and ReDoS-resistant, but doesn't support backreferences, so it can't give full JS parity). Adds roughly 150-300KB to a final stripped binary - negligible next to bundling a JS engine, and the reason regex stays a zero-import core-language literal rather than needing its own std module. |
| **XXHash**         | Extremely fast non-cryptographic hashing                                                                                                        | Internal `Map`/`Set` hashing, package checksums, cache keys                                                                                 |
| **CRC32C**         | Hardware-accelerated checksums                                                                                                                  | Internal integrity checks for `.cp3pak` contents and `.cp3/build/` incremental-compilation cache validity                                       |
| **Boost.Lockfree** | Lock-free queues/stacks                                                                                                                         | Internal runtime queues only (e.g. scheduling for `parallel.*`/async) - lock-free programming is never exposed as a user-facing cp3 concept |
| **libcds**         | Concurrent data structures (if internal lock-free needs exceed what Boost.Lockfree covers)                                                      | Same as above - internal high-concurrency runtime queues only, not a user-facing API                                                        |

None of these change any user-facing syntax or type anywhere in this spec - they're purely implementation choices for making the *compiler's own generated runtime code* fast, in the same way the compiler already generates calls into `std::vector`/`std::variant`/`std::shared_ptr` without the user ever writing those names themselves.
